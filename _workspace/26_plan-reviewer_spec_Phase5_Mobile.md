## 1. 함정 8종 대조 — 태블릿 관점

기존 8종은 이미 확정·구현돼 있다. 여기서는 **"모바일이 되면서 새로 위험해지는 지점"** 만 짚는다.

| # | 함정 | 태블릿에서의 상태 | 새로 짚을 것 |
|---|---|---|---|
| 1 | **번호 3종 분리** | ✅ 그대로 적용. `Defect.seq`(입력순번)만 저장, 출력번호·사진번호는 `numbering.ts` 계산 | ⚠️ **G6 "최근 찍은 번호로 점프"가 어떤 번호인가.** 현장에서 화면에 보이는 풍선 숫자는 `seq`(입력순번)이고, 보고서 번호와 **다르다**. 사용자가 "15번 결함" 이라 부르는 것이 출력에서 8번이 되면 신뢰가 깨진다 → **현장 화면 번호에는 `#` 접두(`#15`)를 붙여 "출력번호가 아님"을 시각적으로 구분한다**(N1). 목업에 반영 |
| 2 | **좌표 0~1 정규화** | ✅ 그대로. 코어 전체가 이미 정규화 기준 | ⚠️ **기하 판정은 스크린 px** 이라는 규칙이 태블릿에서 더 중요해진다. `HIT_PAD_PX=4` 같은 히트 상수가 **마우스 기준**이라 손가락에 그대로 쓰면 못 잡는다 → §5-7 터치 히트 프로파일 |
| 3 | **오프라인 우선** | ✅ 쓰기는 IndexedDB(로컬) 우선 — 이미 그렇다 | 🔴 **읽기 쪽이 아직 없다.** G3 "오프라인 준비"는 *서버에서 미리 받아둔다* 는 뜻인데 **받아올 서버가 아직 없다**. §6 참조. 이게 차단 1 |
| 4 | **항목 계층 = 마스터+연결** | ✅ 용역 생성 시 스냅샷(D6). 태블릿은 스냅샷을 **읽기만** | ⚠️ 현장에서 없는 부재를 즉시 추가하는 경로(D6 근거에 명시됨)를 태블릿에서 **허용할지**. 허용하면 그 추가분이 동기화 병합 대상이 된다 → N2: **허용하되 "이 용역에만" 추가로 제한**(전역 승격은 PC에서만) |
| 5 | **스타일 상속 끊김** | ✅ 그대로 | ⚠️ 태블릿 시트에서 **스타일 탭을 기본 숨김**으로 둔다(현장에서 스타일을 만지면 실수로 개별 스타일이 생겨 전역 설정에서 분리된다). `[더보기]` 안으로 |
| 6 | **면적 계산 단위** | ✅ `project-core/items/size.ts` 공용. 태블릿도 같은 함수 | 없음 |
| 7 | **층 sortOrder(지하 음수)** | ✅ 그대로 | ⚠️ **G6 층 칩 스트립의 정렬이 여기 걸린다.** 하단 칩 스트립은 `sortOrder` 오름차순(지하→지상)으로 고정. 출력 화면(P6)의 "고른 순서 = 번호 순서" 와 **혼동되지 않게** 현장 칩은 번호를 붙이지 않는다 |
| 8 | **전회차 상태 3종** | ✅ PREV_PENDING / CURRENT / REPAIRED | 🟡 **전이 조건이 태블릿에서 처음으로 실제 발동한다.** §2-D는 "촬영하는 순간 CURRENT" 인데 **"촬영 취소"** 를 안 정했다 → §7 Q41 |

**추가 확인 — 출력 재현성**: `ExportRun` 스냅샷은 PC 출력 화면 전용이고 태블릿은 출력을 하지 않는다(§G5 부록 산출물은 사무실 작업). 태블릿이 출력하지 않는 한 재현성 위험은 없다. → **태블릿에 출력 화면을 넣지 않는다**(N3).

## 2. Q6 확정 — 도면 확대 상태에서 정밀 표기 ⭐

> 상세기획 §7 미결 Q6: "도면 확대 상태에서 정밀 표기 방식 (핀치줌 + 크로스헤어? 롱프레스?)"

### 2-1. 결론 (추천안 A · 사용자 확인 요청 = Q38)

> **탭 즉시 찍기를 기본으로 두고, `⊕ 조준` 토글로 "화면 중앙 고정 크로스헤어 + [여기] 확정" 을 켠다.**
> 롱프레스 루페는 채택하지 않는다.

```
평상시 (조준 OFF)
  점 도구 ON → 도면 탭 → 그 자리에 즉시 점 생성      ← 지금 PC 클릭과 완전히 같은 경로

정밀이 필요할 때 (조준 ON)
  화면 정중앙에 십자선이 고정된다 (도면이 아니라 화면에 붙어 있다)
  ├ 한 손가락으로 도면을 민다 / 두 손가락으로 확대한다
  ├ 십자선 아래에 목표가 오면
  └ 오른손 엄지 자리의 [여기] 버튼을 누른다 → 십자선 좌표에 점 생성
     · 십자선은 화면 좌표라 확대·이동과 무관하게 항상 화면 중앙
     · 생성 직후 조준 모드는 유지된다(연속 표기)
```

### 2-2. 왜 이 안인가

| 근거 | 내용 |
|---|---|
| **손가락이 목표를 가리지 않는다** | 정밀 표기가 필요한 순간은 확대 상태다. 확대해도 손가락 접촉면(대략 9~11mm)은 그대로라 목표를 덮는다. 십자선을 화면에 고정하면 손가락은 목표에서 멀리 떨어진 [여기] 버튼 위에 있다 |
| **코어 변경이 0이다** | [여기]는 앱이 **화면 중앙 좌표로 `POINTER_DOWN` + `POINTER_UP` 을 합성**해 기존 `reduce`에 넘기면 끝난다. 점 생성 경로(`interaction.ts` 빈 도면 → PAN 드래그 → UP에서 이동 없으면 점 생성, 739행 부근)를 그대로 탄다. 새 이벤트도, 새 상태도 필요 없다 |
| **좌표계가 안 꼬인다** | 십자선이 화면 좌표라 `toNorm(screen, viewport, iw, ih)` 한 번이면 정규화 좌표가 나온다. 불변식 #1과 충돌 지점이 없다 |
| **젠트릭스도 크로스헤어 계열** | 분석 §2-1: *"점을 누른 채 도면에 터치 → **가이드라인 표시** → 손을 떼면 그 위치에 점 생성"*. 확정 전에 십자 가이드를 보여주는 구조다 |
| **롱프레스는 이미 예약돼 있다** | 롱프레스는 컨텍스트 메뉴(`CONTEXT_MENU`, 코어에 이미 있음)에 배정하는 것이 자연스럽다. 정밀표기까지 롱프레스에 얹으면 충돌한다 |
| **루페는 정밀도를 안 올린다** | 루페(확대경)는 보기만 확대할 뿐 손가락의 물리적 이동 해상도는 그대로다. 확대율이 올라갈수록 1px 떨림이 커져 오히려 손이 떨린다. 렌더도 한 번 더 돌아야 한다 |

### 2-3. 검토했으나 채택하지 않은 안

| 안 | 결과 | 왜 안 뽑았나 |
|---|---|---|
| B. 롱프레스 → 손가락 위 루페 → 드래그로 미세조정 → 뗌 확정 | iOS 텍스트 커서식. 익숙함 | 롱프레스가 컨텍스트 메뉴와 충돌. 루페 렌더 추가. 미세조정 정밀도가 확대율에 반비례해 흔들림 |
| C. 누르는 동안 손가락 **위쪽 40pt** 에 십자선(오프셋 커서) | 손가락이 안 가림 + 한 동작으로 끝남 | 화면 상단 가장자리 결함을 못 찍는다(십자선이 화면 밖). 오프셋 방향을 왼손잡이/오른손잡이별로 바꿔야 함 |
| D. 확대 배율을 올리는 것으로 충분 (별도 UI 없음) | 가장 단순 | ZOOM_MAX=8.0 에서도 손가락 폭은 도면 좌표계로 여전히 크다. 사용자가 "정밀 표기 방식"을 미결로 남긴 이유가 이것으로 해결이 안 됐기 때문 |

### 2-4. 적용 범위

| 도구 | 조준 모드 |
|---|---|
| **점(POINT)** | ✅ 적용. 가장 필요한 곳 |
| **방향(ARROW)** | ⛔ 미적용. 눌러서 끄는 드래그(8방향)라 십자선과 맞지 않는다. 생성 후 `TO` 핸들 드래그로 조정 |
| **영역(AREA_RECT/ELLIPSE)** | ⛔ 미적용. 드래그 생성. 생성 후 8방향 핸들로 조정 |
| **자유그리기(SKETCH)/메모** | ⛔ 미적용 |
| **기존 표기 미세 이동** | ✅ 별도 장치 — 선택 후 시트에 **`↑↓←→` 넛지 패드**(1탭 = 1 스크린 px). 확대 상태에서 손가락 드래그로는 1px 이동이 불가능하다 |

### 2-5. 히트테스트·좌표계 재사용 관계

- `hitTest(screen, screens, selection, memos)` 는 **스크린 px 기준 순수 함수**다. 터치도 스크린 좌표를 넘기므로 **그대로 재사용**한다.
- 다만 임계 상수(`HIT_PAD_PX=4`, `HIT_MIN_MARK_PX=10`, `HIT_MIN_LABEL_PX=12`, `HIT_LEADER_PX=6`, `HIT_STROKE_PX=6`, `HIT_HANDLE_PX=8`, `CLICK_SLOP_PX=4`)가 **모듈 상수**라 플랫폼별로 못 바꾼다 → §5-7에서 프로파일 주입으로 해결.
- 조준 확정 좌표는 `toNorm()` 한 번. 별도 변환 없음.

## 3. G3 확정 — 오프라인 준비 (태블릿 화면·데이터 흐름)

> 상세기획 §Phase 2.5 G3 🔴 치명. *"이건 기능이 아니라 전제 조건이다."*

### 3-1. 상태 모델 (6종)

```
NONE ──[준비 시작]──▶ DOWNLOADING(n%) ──▶ READY
 ▲                          │                │
 │                          ▼                ├─[서버가 갱신됨]──▶ STALE ──[다시 준비]──▶ DOWNLOADING
 └──[기기에서 비우기]────── ERROR ◀───────────┘
                            ▲
                       PAUSED (네트워크 끊김 / 사용자 중지)
```

| 상태 | 칩 표시 | 색 |
|---|---|---|
| `NONE` | `미준비` | 회색 |
| `DOWNLOADING` | `준비 중 62% · 도면 8/13` | 파랑(진행바) |
| `PAUSED` | `일시중지 62%` | 회색 |
| `READY` | `준비완료 · 48MB` | 초록 |
| `STALE` | `갱신 있음` | 노랑 |
| `ERROR` | `실패 · 다시 시도` | 빨강 |

> ⚠️ **색 예약과 충돌하지 않는지 확인함** — 빨강/보라/회색은 *결함 상태* 예약이다(디자인시스템 §3).
> 오프라인 칩은 캔버스 밖 목록 화면이라 결함 마커와 같은 화면에 안 나온다. 다만 목업에서 **결함 색과 시각적으로 구분되도록 pill 형태 + 아이콘**을 함께 쓴다(N4).

### 3-2. 받는 것 / 안 받는 것 (용량 설계)

| 받는다 | 근거 |
|---|---|
| 용역 메타 (`Project`·`Building`·`Floor`·`Drawing` 레코드) | 수 KB |
| **도면 렌더본**(`renderBlobKey`) + 썸네일(`thumbBlobKey`) | 캔버스가 그리는 래스터. **이게 용량의 대부분** |
| 항목설정 스냅샷(`ItemSettings`) | 버튼 그리드가 이것으로 그려진다. 없으면 입력 불가 |
| 전회차 결함 레코드 (`PREV_PENDING`) | 보라 마커 |
| 전회차 **대표사진의 2048px 렌더본 + 320px 썸네일** | §2-D "누르면 이전 사진이 뜬다"의 그 사진 |
| 프리셋 목록 | §2-B 프리셋 탭 |

| 안 받는다 | 근거 |
|---|---|
| **도면 원본**(`sourceBlobKey`: PDF/원본 이미지) | 현장에서 쓰지 않는다. 용량의 절반 이상을 차지한다. 사무실 PC에만 |
| **전회차 사진 원본** | 렌더본으로 충분 |
| 전회차 **비대표** 사진 | 필요하면 온라인일 때 개별 요청 |
| `ExportRun` 이력 | 태블릿은 출력하지 않는다(N3) |

→ **`약 48MB` 는 이 목록의 `byteSize` 합**이다. `Drawing.source.byteSize` 가 이미 저장돼 있어 **서버 왕복 없이 매니페스트만으로 사전 계산된다.**

### 3-3. 매니페스트 (구현 형태)

```
OfflineBundle {
  projectId, revision,            // revision 이 서버와 다르면 STALE
  items: [{ kind, id, blobKey, byteSize }],
  totalBytes, builtAt
}
받은 진행률 = Σ(완료 item.byteSize) / totalBytes
```

- **새 오브젝트 스토어를 만들지 않는다.** `meta` KV 에 `offline:{projectId}` 키로 넣는다 — `ExportRun` 이 쓴 것과 같은 수법(`exportRuns.ts`). **DB_VERSION은 1 그대로, 마이그레이션 0건.**
- 항목 단위 재개(resume)가 가능하다 — 완료된 item 은 다시 안 받는다.

**③ 미준비 경고 다이얼로그 (M-03)** — `READY` 아닌 과업을 열 때
```
 아직 준비되지 않았습니다
 도면 13개 중 5개가 기기에 없습니다.
 현장(오프라인)에서는 그 5개 층의 도면이 열리지 않습니다.

 [지금 준비 (18MB)]   [그래도 열기]   [취소]
```
- **[그래도 열기]를 막지 않는다.** 사무실에서 잠깐 확인하는 경우가 있다. 다만 캔버스 상단에 `오프라인 미준비 — 도면 5개 없음` 배너를 상시 노출.

**④ 설정 — Wi-Fi 자동 준비 (M-01 하단 / 설정 화면)**
- 기본 **ON**. 계량 연결(metered)에서는 동작하지 않는다. 배터리 15% 미만이면 보류.

**⑤ 기기에서 비우기**
- `⋯ → 기기에서 비우기`. **미동기화 변경(사진·결함)이 남아 있으면 차단**하고 `먼저 서버로 보내야 합니다 — 미전송 12건` 을 띄운다. 이걸 안 막으면 현장 데이터가 사라진다.

### 3-5. 불변식 재확인

> **오프라인 준비는 "읽기 캐시"일 뿐이다. 쓰기 경로에는 아무 영향이 없다.**
> 준비가 안 된 상태에서도 결함 입력·사진 촬영은 로컬 IndexedDB 에 그대로 들어간다.
> 안 되는 것은 "도면 이미지가 없어 캔버스에 배경이 안 뜨는 것" 하나뿐이다. (규칙 3 유지)

## 5. 결함 입력 시트 — 태블릿 레이아웃 확정

### 5-1. 가장 큰 결정: **화면 방향에 따라 시트 방향이 바뀐다**

| 방향 | 시트 | 이유 |
|---|---|---|
| **가로(landscape)** 10~13" | **우측 사이드시트** 폭 400pt (PC와 같은 구조) | 가로 화면은 세로가 짧다(예: 1194×834). 바텀시트를 55% 올리면 도면 하단이 통째로 가려진다. 우측을 400pt 떼도 캔버스가 794×834 로 여전히 넓다 |
| **세로(portrait)** | **바텀시트** 3단 스냅 | 세로 화면은 가로가 좁다(834pt). 사이드시트를 붙이면 캔버스가 434pt 로 쪼그라들어 도면을 못 본다 |
| **폰** | 바텀시트 3단 (열 수만 줄임) | |

> §2-B 원문 *"PC = 우측 사이드시트 / 모바일 = 바텀시트"* 는 **폰 기준의 서술**로 읽는다.
> 태블릿 가로는 물리적으로 PC에 가까우므로 사이드시트가 맞다. **이건 기획서를 뒤집는 게 아니라 태블릿이라는 중간 크기를 추가로 정의하는 것**이다. → 사용자 확인 요청(Q39, 비차단)

### 5-2. 바텀시트 3단 스냅 (세로)

| 스냅 | 높이 | 보이는 것 |
|---|---|---|
| **PEEK** | 화면 16% (≈ 130pt) | 한 줄 요약 `#42 벽(구조체) · 수직균열 0.2×2000 2ea` + 사진 칩 3개 + `[📷]` |
| **HALF** | 55% | 사진 스트립 · 부재 · 결함유형 · 규모(폭/길이/개수) — **여기서 90%가 끝난다** |
| **FULL** | 92% | 위 + 진행여부·누수·발생원인·보수방안·위치보조·메모 + `[더보기]`(스타일) |

- 손잡이(grabber) 드래그로 이동. 시트 밖 캔버스 탭 → PEEK 로 내려감(닫히지 않는다).
- **결함 선택 = 최소 PEEK 이상**. 선택 없이 시트가 열려 있지 않는다.
- 키보드가 뜨면(직접입력) 자동으로 FULL. 키보드가 닫히면 원래 스냅으로 복귀.

### 5-3. `SET_SAFE_INSETS` 연결 — 여기가 핵심이다

코어에 **이미 있다** (`CanvasState.safeInsets`, `InputEvent.SET_SAFE_INSETS`, `visibility.applyEnsureVisible`).

```
시트 높이가 바뀔 때마다  →  SET_SAFE_INSETS { bottom: 시트높이 + 홈인디케이터, ... }
                       →  keepSelectionVisible() 이 선택 결함을 시트 위로 밀어 올린다
사이드시트(가로)         →  SET_SAFE_INSETS { right: 400 }
```
→ **"방금 찍은 결함이 시트 뒤에 숨는" 최악의 현장 버그가 코어 변경 없이 막힌다.** 목업에도 이 여백을 반영한다.

### 5-4. PC와 같은 점 / 다른 점

| | 같은 점 | 다른 점 |
|---|---|---|
| **필드 구성·순서** | 완전히 동일 (§2-B 골격 그대로) | — |
| **기본값·규모모드 교체** | 동일 (`sizeMode=AREA` → 면적 블록 교체) | — |
| **직전 입력 기억(D9)** | 동일 (`defectSeed`) | — |
| **컴포넌트** | `ui/defectForm/*` 재사용 — store·repo·캔버스 import 금지 규칙 덕에 **props만 넘기면 그대로 산다**(`DefectInfoForm{value, settings, onChange, disabled}`) | 렌더러만 교체(§6-2 런타임 결정에 따라) |
| **터치 타깃** | | PC 28~32px → **최소 44×44pt**, 버튼 간 간격 8pt |
| **그리드 열 수** | | 가로 사이드시트 **3열** / 세로 바텀시트 **4열** / 폰 **3열** |
| **사진 진입점** | | PC = 파일 선택 → 태블릿 = **`[촬영]` 이 1순위**, `[앨범]` 이 2순위 |
| **스타일 탭** | | **기본 숨김**(`[더보기]` 안). 함정 #5 |
| **직접입력** | | 숫자 키보드(`inputMode="decimal"`)만. 시트가 FULL 로 올라감 |
| **넛지 패드** | 없음 | **있음** — 선택 표기 1px 이동 (§2-4) |

### 5-5. 젠트릭스 §2-7 레이아웃을 그대로 베끼지 않는 이유 (명시)

젠트릭스 §2-7 실측(`좌 사이드바 | 캔버스 | 우 속성패널 + 우측 세로 툴바 + 하단 액션바`)은 **PC/웹 화면**이다.
태블릿에 3분할을 그대로 얹으면 캔버스가 절반 이하로 줄어든다. 태블릿은 **캔버스 우선 + 오버레이**로 간다:

| 젠트릭스 PC | 태블릿 대응 |
|---|---|
| 좌 사이드바(동·층·조사항목) | **하단 층 칩 스트립** + `[≡ 리스트]` 버튼으로 여는 **좌측 슬라이드 시트** |
| 우 속성패널 | **가로=우측 사이드시트 / 세로=바텀시트** (§5-1) |
| 우측 세로 툴바 | **좌측 세로 툴바**(왼손 엄지). 5개 아이콘: 선택 / 점 / 방향 / 영역 / 그리기 + `⊕조준` |
| 하단 액션바 8개 | **상단 얇은 바 3개**(되돌리기·다시실행·⋯) — 나머지는 `⋯` 메뉴. 하단은 시트가 쓴다 |

> 오프라인 준비(G3)만은 서버 설계가 먼저다 — 이건 태블릿 앱의 문제가 아니라 Phase 5 전체의 전제다.**
