## AD4 · 🔴 GitHub 푸시 불가 — 로컬 커밋만으로 계속 진행 · 2026-08-23

**무엇을 결정해야 했나:**
1번 항목(F3+F6) 커밋 후 `git push origin main` 이 403 으로 실패했다.
`Claude doesn't have GitHub access to uk2y-getitgit/OnSpect_build for your organization` —
조직에 Claude GitHub App 이 설치돼 있지 않거나 쓰기 권한이 없다는 뜻이다.
대안으로 GitHub MCP 서버의 `push_files`(REST API 경유)를 시도했으나 역시
`POST .../git/trees: 403 Resource not accessible by integration` 로 거부됐다.
읽기(`get_file_contents`)는 되지만 **쓰기는 이 세션 전체에서 막혀 있다.**

**왜 임의로 우회하면 안 되는가:**
- 프록시 안내문(`/root/.ccr/README.md`)이 명시: *"do not retry organization policy denials
  (403/407) — report them instead"*. 조직 정책 차단은 내가 풀 수 있는 문제가 아니다.
- 이 컨테이너는 비활성 시 회수될 수 있다 — 푸시가 안 되면 지금까지·앞으로의 로컬 커밋이
  **전부 사라질 위험**이 있다. 사용자가 지금 알아야 조치(GitHub App 설치·재연결)를 할 수 있다.

**선택지:**
A. 푸시가 안 되니 작업을 여기서 멈추고 사용자 확인을 기다린다
B. **알림으로 즉시 보고한 뒤, 로컬 커밋은 계속 남기며 나머지 항목을 진행한다**

**내가 고른 것:** B

**근거:**
- 브리프(§4)는 "항목마다 커밋하고 푸시하라. **푸시가 실패하면 커밋만이라도 남기고 보고에
  적어라**"고 명시한다 — 푸시 실패가 작업 중단 사유가 아니라 "커밋은 계속하되 보고하라"는
  뜻으로 읽힌다.
- 이 실행의 목적(§1)은 "갈 수 있는 데까지" 진행하는 것이고, 사용자는 자리에 없어 지금 답할
  수 없다. 로컬 저장소에 성과가 쌓이는 것 자체는 손해가 아니다 — 컨테이너가 살아있는 한
  검증 가능한 커밋 이력으로 남고, 세션이 이어지면(같은 컨테이너로 재접속) 그대로 푸시할 수 있다.
- PushNotification 으로 **즉시** 알렸으므로 "조용히 계속 진행"이 아니다. 사람이 원하면
  언제든 개입해 멈출 수 있다.

**되돌리는 비용:** 낮음 — 이 판단을 뒤집는 것은 "이후 항목을 중단"하는 것뿐이고, 이미 만든
로컬 커밋은 손실이 없다(원격에 아직 아무것도 안 올라갔으므로 충돌도 없다).

**사용자 확인 필요도:** **높음** — 이건 판단이 아니라 **막힌 인프라 문제**다. 조직 관리자가
https://github.com/apps/claude/installations/select_target 에서 Claude GitHub App 을
이 저장소에 쓰기 권한으로 설치하거나, claude.ai 설정에서 GitHub 커넥터를 재연결해야 풀린다.

**이후 방침:** 각 항목 완료 시 로컬 커밋은 계속하고, `git push` 는 **1회만** 시도한다
(정책 차단을 반복 재시도하지 않는다 — 프록시 안내 원칙). 세션 종료 전 마지막에 한 번 더
전체 재시도한다.

## AD5 · F4 — 라벨 예외를 어디에 넣을 것인가 · 2026-08-23

**무엇을 결정해야 했나:**
`onPointerDown` 에서 생성 도구(ARROW·AREA_RECT·AREA_ELLIPSE·SKETCH)가 켜져 있으면
`hitTest` 를 전혀 안 부르고 곧장 `startCreateShape`/`startCreateSketch` 로 분기하고 있었다
(주석: "도구를 켜 놓고 도형 위에서 시작하는 것은 저 위에 새로 그린다는 뜻"). 그래서 번호
풍선(LABEL) 위를 클릭해도 무조건 새 표기가 생성됐다 — F4 가 지적한 버그의 정확한 원인.
이 우회를 어떻게 예외 처리할지가 문제였다.

**선택지:**
A. 히트 테스트를 **항상 먼저** 돌리고, `hit.part === 'LABEL'` 일 때만 도구 생성을 건너뛴다
B. 라벨만 별도로 가벼운 원형 판정을 새로 만들어 도구 분기보다 앞에 둔다 (히트 테스트 우선순위
   로직을 두 벌로 만드는 방식)

**내가 고른 것:** A

**근거:**
- `hitTest()` 내부는 이미 "1. 라벨"을 최상위 우선순위로 판정한다(§2-4 문서화된 순서).
  B 안은 그 판정을 별도로 재구현해야 하고, 반경·풍선 크기 계산이 두 곳에서 어긋날 위험이 생긴다.
- A 안은 기존 `hitTest` 를 그대로 재사용하고, "도구가 켜져 있어도 **라벨**이 아니면 그대로
  생성한다"는 조건 하나만 추가하면 된다 — 다른 표기(점·화살표·영역·자유그리기) 위에서는
  기존 의도(도구가 이긴다)가 그대로 유지된다.
- 다만 이제 생성 도구가 켜져 있을 때도 매 클릭마다 `hitTest` 를 한 번 돈다(이전엔 즉시 생성
  분기로 건너뛰었다). 결함 수가 많아도 O(n) 순회 한 번이라 비용은 무시할 만하다.

**되돌리는 비용:** 낮음 — `interaction.ts::onPointerDown` 상단 20줄. `labelGrabbed` 조건 하나만
빼면 기존(F4 이전) 동작으로 복귀한다.

**커서(hover) 는 이미 문제 없었다** — `onPointerMove` 의 호버 계산은 애초에 도구와 무관하게
매번 `hitTest` 를 돌리고 있었다. `computeCursor` 도 `state.hover` 가 있으면 도구를 보지
않고 `move`/`pointer` 를 반환한다. 그래서 "풍선 위에서 커서가 move 로 바뀐다"는 요구는
**이미 충족돼 있었고**, 이번에 고친 것은 **pointerdown 의 동작**뿐이다.

**검증:** ARROW·AREA_RECT·AREA_ELLIPSE·SKETCH 4개 도구 각각에 대해 "라벨을 누르면
`MOVE_LABEL` 드래그가 시작되고 결함이 새로 생기지 않는다"는 테스트, "라벨이 아닌 빈
자리는 그대로 생성된다"는 회귀 테스트, "잠긴(전회차) 결함의 라벨은 도구가 켜져 있어도
선택만 되고 끌리지 않는다"는 테스트를 `s2a.test.ts` 에 추가했다(+6). 기존 209개 + 6 = 215개
전부 통과.

**사용자 확인 필요도:** 낮음 — 스펙(F4)이 요구한 동작 그대로이고, 다른 표기 위의 도구
동작은 전혀 안 바뀌었다.

## AD6 · S4 — `apply.ts` 는 canvas-core 를 import 하지 않는다(D13) · 2026-08-23

**무엇을 결정해야 했나:**
plan-reviewer 스펙(§4-2)의 `apply.ts` 함수 시그니처는 `setStructureType(a: DefectAttrs, …): DefectAttrs`
처럼 **`DefectAttrs`(canvas-core 타입)를 그대로 쓴 코드**였다. 그런데 D13(`project-core` 와
`canvas-core` 는 서로 import 하지 않는다 — 잇는 것은 `apps/web` 의 책임)이 이미 확정 규칙이고,
`apply.ts` 는 `project-core` 안에 있다. 스펙 문서의 코드 스니펫을 문자 그대로 따르면 D13 을 깬다.

**선택지:**
A. 스펙 스니펫 그대로 `@onspect/canvas-core` 를 import 해서 `DefectAttrs` 를 쓴다 (D13 위반)
B. `project-core` 안에 **구조적으로 동일한 로컬 타입**(`AttrsLike`)을 선언하고 제네릭
   (`<T extends AttrsLike>`)으로 함수를 짜서, 실제 `DefectAttrs` 값이 그대로 들어가게 한다

**내가 고른 것:** B

**근거:**
- D13 은 이번 실행보다 먼저 확정된 규칙이고, S1 때부터 지켜왔다(`ASSUMPTIONS.md` D13).
  스펙 스니펫은 그 경계를 검토하기 전에 쓰인 의사코드로 보인다 — 실제 구현 지시가 아니다.
- TypeScript 는 구조적 타이핑이라 `AttrsLike` 를 `DefectAttrs` 의 부분집합으로 선언하면,
  `apps/web` 이 진짜 `DefectAttrs` 객체를 넘겨도 **아무 캐스팅 없이** 그대로 맞는다.
  제네릭 `<T extends AttrsLike>` 를 쓴 이유는 `apply.ts` 가 모르는 필드(`progress`·`leak`·`memo`
  등)도 스프레드로 그대로 보존되게 하기 위해서다 — 안 그러면 함수가 그 필드들을 지워버린다.
- `size.ts` 도 같은 원리로 `SizeInput` 이라는 로컬 타입을 쓴다. 패턴이 일관된다.

**되돌리는 비용:** 낮음 — `AttrsLike` 를 `DefectAttrs` 로 바꾸는 것은 import 한 줄과 타입 참조
교체뿐이다. 다만 그러면 D13 을 다시 어기게 되므로 권장하지 않는다.

**사용자 확인 필요도:** 낮음 — 동작은 스펙과 동일하고, 경계 규칙만 지킨 것이다.

## AD7 · S4 — `seedAttrs` 는 전체가 아니라 **패치**를 돌려준다 · 2026-08-23

**무엇을 결정해야 했나:**
스펙은 `seedAttrs(s, project): DefectAttrs` (전체 반환)로 적었다. 하지만 "새 결함의 초기값
전부"(`surveyKind: 'EXTERIOR'`, `leak: false` 등)는 `EMPTY_DEFECT_ATTRS` 라는 이름으로
**canvas-core 에 이미 정의돼 있다.** `project-core` 가 그 상수를 몰래 다시 베끼면(D13 경계를
지키려고 로컬 상수를 또 만들면) 두 값이 나중에 어긋날 위험이 생긴다(canvas-core 쪽 기본값이
바뀌어도 project-core 쪽은 그대로 남는다).

**선택지:**
A. `project-core` 안에 `EMPTY_ATTRS` 를 통째로 복제해 전체 `DefectAttrs` 모양의 객체를 돌려준다
B. **패치**(`Partial<AttrsLike>`)만 돌려주고, 합치는 것은 호출자(`apps/web`)의 책임으로 남긴다

  절대 규칙**이다. 옛 텍스트 메모와 새 손글씨 메모가 **한 스토어에 공존**하게 되므로,
  렌더러·히트테스트·`memoGeom.ts`·`ContextToolbar`·기존 메모 관련 단위테스트 10여 개를
  전부 다시 설계해야 한다. **이건 "데이터 구조를 굳히는 판단"이라 확인 필요도가 원래
  높음으로 표시돼야 할 사안**인데, 사람이 없는 지금 굳혀 버리는 것은 §2 규칙의 취지에
  맞지 않다고 판단했다.

**②·③에 대해 미리 남기는 설계 메모** (다음 시도에서 다시 고민하지 않도록):
- ②: `CanvasState.pendingSketch: { points: NPoint[]; width: number } | null`. 그리기 커밋 시
  선택된 결함이 없으면(현재처럼 토스트로 버리지 않고) 이 필드를 채운다. 대기 중엔 **모드 전환
  없이** — 기존 표기를 클릭하면 그 결함에 바로 붙고, 빈 곳을 클릭하면 계속 대기하며, 별도
  플로팅 패널의 `[새 결함으로]`(중심점에 POINT 마크로 새 결함 생성 + 스케치 첨부)와 `[취소]`
  버튼을 둔다. Escape 로도 취소된다. 대기 중에는 도구를 바꿔도 유지한다(F4 와 같은 정신 —
  실수로 잃으면 안 된다).
- ③: `Memo` 에 `paths?: SketchPath[]` 를 **추가**하고 `text` 는 그대로 둔다(옛 레코드
  호환). 렌더는 `paths` 가 있으면 손글씨로, 없으면(옛 레코드) 텍스트 상자로 그린다 —
  `normalizeDefectAttrs` 와 같은 "읽기 정규화, DB 버전 유지" 패턴을 그대로 따르되, 여기는
  값을 만들어 채우는 게 아니라 **렌더 분기**로 처리해야 한다(빈 손글씨를 만들어낼 수 없다).
  색은 중립색 유지, 질감은 표(§ F2 "그리기 ≠ 메모")대로 실선이 아닌 것(점선 권장)으로.

**되돌리는 비용:** 낮음(①은 이미 끝났고 되돌릴 필요가 없다) — ②·③은 **아직 손대지 않았으므로
되돌릴 것도 없다.** 위 설계 메모가 시작점이 된다.

**사용자 확인 필요도:** ①은 낮음. ②·③ 착수 여부는 **높음** — 특히 ③은 데이터 구조를
굳히는 판단이라 사용자가 "메모를 정말 손글씨 전용으로 바꿀지, 텍스트도 계속 지원할지"를
먼저 확인하는 편이 안전하다.
