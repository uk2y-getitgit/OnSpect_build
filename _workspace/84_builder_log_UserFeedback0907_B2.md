## 항목 A (D46) — 파일 가져오기 시 같은 용역 감지 → 확인창

### 설계 요약

`[파일에서 가져오기]` 를 **두 단계**로 쪼갰다. 지금까지는 "파일 열기 → 곧장 심기" 한 덩어리라
중간에 물을 자리가 없었다.

```
readProjectZip(file)              zip 열기 + manifest 검증. 아무것도 저장하지 않는다
  → 이름·연도·반기·종류가 전부 같은 기존 용역 찾기 (순수 판정, project-core)
  → 후보 0건  : 곧장 importParsedProject(..., { kind: 'NEW' })      ← 지금까지와 동일
  → 후보 1건+ : ImportDuplicateDialog 로 묻는다
                  [새로 만들기]  → { kind: 'NEW' }        (id 전부 새로 발급 — D38 그대로)
                  [덮어쓰기]     → { kind: 'OVERWRITE', projectId }
                  [취소]         → 아무 일도 없음
```

**덮어쓰기의 핵심 두 가지**

1. **`project.id` 만 기존 값으로 고정한다.** `remapTransferBundle` 은 그대로 쓰되, id 맵을
   다 채운 뒤 `idMap.set(파일의 project.id, 기존 project.id)` 한 줄로 되돌린다. 나머지
   (동·층·도면·결함·마크·메모·사진·항목설정)는 전부 새 id 를 받는다.
   → 서버 동기화가 붙어 있으면 **같은 용역으로 계속 이어진다**.
   → 항목설정 스냅샷 id 는 `projectId` 와 같은 값이라(`ensureProjectSettings` 가 projectId 를
     키로 쓴다) 같은 map 항목을 함께 타고 들어간다. 별도 처리 불필요.

2. **삭제 + 삽입이 한 트랜잭션.** `repo.importBundle({ replaceProjectId })` 가 같은
   `readwrite` 트랜잭션 안에서 기존 하위 레코드를 먼저 지우고 새 레코드를 넣는다.
   "다 지워졌는데 안 들어온" 반쪽 상태가 존재할 수 없다(`putDrawingWithBlob`·`registerPhotos`
   와 같은 관례).

**덮어쓰기가 정리하는 것** (`purgeProjectContentsIn`)

| 대상 | 처리 |
|---|---|
| 사진·도면 | 레코드 삭제 + Blob refCount 해제 + objectURL 무효화(`revokeUrl`) |
| 결함·메모·층·동 | 레코드 삭제 |
| 삭제 전파 기록(D25) | 6종 전부 tombstone 기록 — **없으면 다음 pull 에서 옛 결함이 되살아난다** |
| `lastView:{projectId}` | 삭제 — 새로 발급된 도면 id 와 어긋난 기억을 남기지 않는다 |
| `Project` 레코드 자신 | **안 지운다** (id 를 살려야 동기화가 이어진다). 파일 내용으로 `put` |
| 항목설정 | 지우지 않고 `put` 으로 덮는다 — 상세는 아래 "알려진 한계" |

성능: 삭제 기록을 건당 남기면 `meta` 를 N번 읽고 N번 쓰며 배열 filter 도 매번 돈다.
결함 수백 건짜리 용역에서 그대로 지연이 되므로 **일괄 append** 를 새로 만들었다
(`appendDeletions` + `recordDeletions` — 읽기 1회·쓰기 1회). 한 건씩 지우는 기존 경로
(층·도면·사진 삭제)는 지금처럼 `recordDeletion` 을 계속 쓴다.

**자동 덮어쓰기는 하지 않는다** (D46). 이름은 고유 키가 아니라, 넷이 다 같아도 서로 다른
용역일 수 있다. 후보가 여러 건이면 어느 것을 덮어쓸지 라디오로 고르게 했다(기본값 = 목록
맨 위 = 가장 최근 접속).

## 항목 B (D47) — 전차 사진 조회 (참조 공유, 복제 없음)

### 설계 요약

전차(`PREV_PENDING`) 결함을 선택하면, `defect.prevDefectId` 가 가리키는 **전회차 결함의
사진**을 우측 패널의 사진 섹션 **아래에 별도 섹션**으로 붙인다.

- **Blob 을 복제하지 않는다** (D47 B안). 새 용역에 사진 레코드를 만들지 않고, 그때그때
  원본에서 찾아 보여주기만 한다 → 저장 공간이 안 늘고, 원본이 남아 있는 한 항상 최신.
- **`DB_VERSION` 무변경.** `photos` 스토어에 `by_defect` 인덱스가 **이미 있었고**
  `repo.listPhotosOfDefect(defectId)` 도 이미 있었다 — 그대로 쓴다. 새 인덱스·마이그레이션 없음.
  (`prevDefectId` 가 가리키는 결함이 다른 `projectId` 에 있어도 `by_defect` 조회는 그대로 맞는다)
- **원본이 이 기기에 없으면 조용히 사라진다.** 조회 결과가 0장이면 섹션 자체를 그리지 않는다 —
  토스트도 에러도 없다. 사진이 0장인 경우와 같은 처리다.
- **편집 경로가 하나도 없다.** 삭제·회전·자르기·대표지정·캡션·순서변경 전부 미구현.
  `PhotoPreviewDialog` 를 `disabled` 로 재사용하지 않고 **읽기 전용 뷰어를 따로** 만들었다 —
  그 창은 캡션 입력·자르기·주석 편집을 품고 있어서, 붙이는 순간 **다른 용역의 데이터**를
  이 화면에서 고칠 길이 생긴다. prop 하나로 막는 것보다 편집 코드가 없는 편이 안전하다.
- 크게보기는 `usePhotoComposite`(읽기 전용 훅)로 **전회차에서 지정한 자르기·주석까지 그대로**
  보여준다. 썸네일은 합성하지 않고 `✎` 배지만 띄운다(기존 R1 규율과 동일).
- 구분: 왼쪽에 전차색(`--defect-prev`, 남색) 띠 + 제목 옆 `보기 전용` 배지.

## 알려진 한계

1. **항목설정 스냅샷은 덮어쓰기에서 "지우지 않고 덮는다."**
   `ItemSettings.id === projectId` 라 가져온 설정을 `put` 하면 같은 키를 덮어쓴다.
   다만 파일에 항목설정이 **없는** 경우(옛 백업 파일)에는 기존 설정이 그대로 남는다.
   일부러 이렇게 했다 — 지워 버리면 `ensureProjectSettings` 가 **지금 조직 설정**으로 새
   스냅샷을 떠서 불변식 #7(과업 시점 스냅샷)을 어긴다.

2. **`exportRun:` 기록은 덮어쓰기에서 안 지운다.** 옛 출력 스냅샷이 사라진 결함 id 를 가리킨
   채 남는다. 재다운로드 시 옛 번호가 재현되는 것이 원래 의도이므로 지우지 않았다. 다만
   덮어쓰기 후 그 스냅샷은 현재 데이터와 대응되지 않는다 — 필요하면 별도 결정 사항.

3. **전차 사진의 objectURL 은 "현재 용역" 소유로 등록된다.**
   `urlCache` 가 blobKey → { url, projectId } 인데, 전차 사진 URL 도 **지금 보고 있는 용역**
   id 로 태깅된다. 현재 용역을 나갈 때 정리되므로 누수는 없다. 다만
   `금차 용역에서 전차 사진 보기 → 전차 용역으로 이동 → 같은 사진 보기 → 금차 용역 나가기`
   순서로 오가면 전차 용역 화면의 그 사진 URL 이 먼저 해제될 수 있다(이미지가 깨져 보임).
   기존 URL 캐시 설계에서 오는 것이고 새로 만든 문제는 아니다 — 발견되면 별도 수정.

4. **전차 사진에 결함번호·사진번호를 붙이지 않는다.** 출력 번호는 저장하지 않는다(불변식 #2)
   — 다른 용역의 번호를 이 화면에서 계산해 보여주면 그 자체가 오해를 만든다. 파일명만 보인다.

5. **동시 작업 주의** — 이번 커밋은 `CanvasRoute.tsx` 를 건드렸다(배율 함수가 아니라
   `photoSlot` JSX 한 곳). 다른 에이전트의 배율 작업과 같은 파일이므로, 리베이스·머지 시
   그 구간만 확인 필요.
