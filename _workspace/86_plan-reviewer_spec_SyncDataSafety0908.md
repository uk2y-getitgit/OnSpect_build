## 1. 지금 설계로 이미 안전한 것 (근거: `packages/project-core/src/lww.ts`, `apps/web/src/data/sync.ts`)

**결론부터: "같은 용역, 서로 다른 도면(층)에서 작업"은 지금 구조로 이미 안전하다.**
데이터 유실을 만들려면 **같은 레코드**를 두 기기가 동시에 건드려야 하는데, 다른 도면 작업은
서로 다른 `Floor`/`Drawing`/`Defect`/`Mark`/`Photo` id를 만들기 때문에 애초에 부딪히지 않는다.

| 구조 | 왜 안전한가 |
|---|---|
| 레코드 단위(용역·동·층·도면·결함·마크·메모·사진·항목설정 9종) 각자 `id`+`updatedAt`+`deviceId` | A가 만든 결함과 B가 만든 결함은 id가 다르다 → 병합 대상이 아니라 **둘 다 살아남는 추가(add)** |
| `syncProject()`가 매번 **서버 레코드 전체 색인**을 훑어 로컬과 비교(커서에 의존하지 않음) | D41에서 발견된 `server_seq` 결함(값이 안 오름)을 이미 이 방식으로 우회해뒀다 — "새 레코드를 놓친다"는 실패모드가 구조적으로 없다 |
| 삭제는 `meta` KV에 tombstone(D25)으로 따로 쌓고, push 때 서버 값보다 최신일 때만 전파 | 삭제와 신규 추가가 섞여도 삭제 쪽이 조용히 다른 걸 지우지 않는다 |
| 충돌(LWW 패배) 시 **진 쪽 레코드를 그대로 `meta` KV에 보관**하고 `[동기화]` 버튼 옆에 `충돌 N건 보기`로 노출 | "말없이 사라짐"은 이미 없다 — 최소한 로그로는 남는다(`SyncButton.tsx`) |
| Blob(사진·도면 원본) 업/다운로드는 **레코드 revision과 무관하게 매번 전체 스캔**해서 빠진 것만 재시도 | 업로드 1회 실패해도 다음 동기화에서 자동 재시도(예전엔 이게 안 돼서 "영원히 빈 도면" 버그였다 — 이미 고쳐짐) |

즉 "여러 사람이 각자 로그인해서 같은 프로젝트의 서로 다른 도면을 작업 → 각자 `[동기화]` 클릭"
루틴은 **지금 코드 그대로도 유실 없이 합쳐진다.** 실사용 확인(D46/D47 체크리스트의 "두 기기 병합"
계열 항목)으로 검증하면 되고, 별도 구현이 필요 없을 가능성이 크다.

## 2. 그래도 남는 위험 — 실제로 유실/오염이 생기는 3가지 시나리오

"다른 도면"이 아니라 **같은 레코드를 두 사람이 동시에 건드리는 경우**에서만 발생한다.

### 시나리오 A — 진짜 필드 유실 (기존에 이미 알려진 설계, 이번에 새로 발견한 것 아님)
같은 결함(같은 id)을 A·B 둘 다 동기화 없이 고치고 각자 동기화하면, 나중에 이기는 쪽이
**레코드 전체를 통째로** 덮는다(`lww.ts` 원칙 — 필드 단위 병합 안 함). 진 쪽 수정은 사라지고
`meta` KV의 JSON 뷰어에만 남는다(위 §1 표). **"다른 도면 작업"이면 애초에 안 일어난다** —
같은 결함을 같이 고칠 때만.

### 시나리오 B — 삭제-추가 경합으로 고아 레코드 발생 (이번에 코드에서 새로 확인)
1. A가 층 X를 삭제한다 → 로컬에서 그 층의 도면·결함·메모·사진까지 **연쇄 삭제 + tombstone
   전부 기록**(`repo.ts::purgeFloorIn`) — 단, **그 순간 A의 로컬에 있던 것만** 기록한다
2. 그 직전에 B가 (A의 삭제를 아직 못 받은 채) 층 X에 결함을 새로 만들고 **먼저 동기화**한다
3. A가 동기화한다 → A의 tombstone은 층 X를 지운다. 그러나 **B가 만든 새 결함은 A가 존재조차
   몰랐던 것이라 tombstone 목록에 없다** → 서버에 살아남는다
4. 결과: 서버·다른 기기들에 "층은 없는데 그 층을 가리키는 결함 하나가 남아있는" 상태가 생긴다.
   `floors.find(f => f.id === floorId)`가 `undefined`를 반환하는 지점이 최소 `CanvasRoute.tsx`·
   `ProjectSetup.tsx` 등 3곳 이상 확인됨(방어 코드 없음 — 결과 미검증, 화면에서 조용히 안 보이거나
   콘솔 에러가 날 수 있음)

**발생 조건이 좁다**(같은 층을 몇 초~몇 분 사이에 한쪽은 삭제, 한쪽은 추가) — 하지만 "각자 로그인해서
같은 용역을 동시에 만진다"는 이번 요청의 전제 자체가 이 조건을 만들 수 있는 상황이다.

### 시나리오 C — 동기화 간격이 벌어질수록 A·B 위험 확률이 커짐
지금은 **완전 수동**이다(`[동기화]` 클릭 때만 네트워크, 자동 동기화 없음 — D39 설계 그대로).
하루 종일 동기화 없이 각자 작업하면 A·B 케이스가 부딪힐 창이 넓어진다. 이건 버그가 아니라
"운영 습관"의 문제지만, 이번 요청("데이터 유실 없게 하고 싶다")의 실질적 원인이 될 수 있다.

## 3. 제안 작업 (난이도 낮은 순 — 어디까지 할지는 질문 3건으로 사용자 결정 필요)

| # | 작업 | 막는 것 | 난이도 | 데이터 구조 변경 |
|---|---|---|---|---|
| S-1 | 동기화 버튼 옆에 "마지막 동기화 : n분 전" 상시 표시 + 오래됐으면(예: 1시간+) 색 강조 | 시나리오 C(동기화 습관) | 낮음 | 없음(`SyncState.lastSyncedAt` 이미 있음) |
| S-2 | 용역 목록/캔버스 진입 시 **가벼운 서버 색인만** 조회해 "서버에 새 변경 있음" 배지(자동 반영은 안 함, 클릭해야 동기화) | 시나리오 C | 중간 | 없음(읽기 전용 호출 추가) |
| S-3 | pull 단계에서 **자기 지역에 없는 층/도면을 참조하는 결함**을 걸러 "고아 결함 N건" 경고 배너로 모아 보여주기(숨기지도 삭제하지도 않음, 사용자가 판단) | 시나리오 B | 중간 | 없음(런타임 필터) |
| S-4 | tombstone 전파 시 "그 층/도면 id를 참조하는 서버측 자식 레코드"까지 서버가 함께 지우도록 push 로직 보강(자식 재스캔) | 시나리오 B 원천 차단 | 높음 | `syncProject()` 삭제 단계 로직 확장, 되돌리기 어려운 삭제 로직이라 신중 필요 |
| S-5 | 충돌 뷰어에 "이 값으로 다시 올리기" 버튼(진 쪽 레코드를 새 `updatedAt`으로 재푸시) | 시나리오 A 복구 | 중간 | 없음(기존 `SyncConflict.local` 재사용) |

**추천 조합:** S-1 + S-3 (+ 필요시 S-2). 둘 다 **기존 데이터를 하나도 안 건드리고**, 서버 삭제
로직(가장 위험한 부분)에 손을 안 대면서 시나리오 B·C의 체감 위험을 실질적으로 낮춘다. S-4는
"삭제 연쇄"라는 가장 되돌리기 비싼 영역이라 **지금 실사용에서 문제가 실제로 드러난 뒤** 착수를
권한다(Q87 때와 같은 판단 기준). S-5는 우선순위 낮음(개인 테스트 단계에서 A/B 동시편집 자체가
드묾).
