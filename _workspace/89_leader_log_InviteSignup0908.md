## 무엇을 만들었나

### 서버 (`supabase/migrations/20260908000000_invite_codes.sql`)

- `invite_codes` 테이블 — 코드(8자, PK)·팀·만료일(선택)·사용횟수·취소 플래그.
- RLS — select/insert/update 전부 `is_team_owner()`(팀장만). 팀원이 조회해도 빈 목록.
- `check_invite_code(code)` — anon 도 부를 수 있는 사전 검사 RPC. 가입 폼이 "가입" 누르기
  전에 먼저 이걸로 확인해, 오타·만료 코드로 쓸모없는 계정이 만들어지는 걸 막는다.
- `handle_new_user_invite()` — **`auth.users` INSERT 트리거**(SECURITY DEFINER). 가입 순간
  `raw_user_meta_data.invite_code` 를 읽어 코드를 재검증하고, 유효하면 `team_members` 에
  `role='MEMBER'` 로 자동 합류시킨다. 코드가 무효하면 예외를 던져 **가입 자체가 롤백**된다 —
  service role 키도, 새 서버리스 함수도 없이(D40 유지) RLS 를 우회하는 유일한 지점이다.

### 가입 화면 (`Login.tsx` + `session.tsx`)

- 로그인 화면에 "가입" 모드 토글을 넣었다 — 이메일·비밀번호·초대코드 3칸.
- `session.tsx::signUp` — `check_invite_code` 로 미리 확인 → `auth.signUp` (코드를
  `options.data.invite_code` 로 동봉) → 성공하면 즉시 로그인 상태로 전환(이메일 확인이 켜져
  있으면 세션이 안 오므로 "이메일을 확인해 주세요" 안내로 로그인 화면에 남는다).
- 트리거가 던진 예외의 원문이 클라이언트까지 그대로 오는지 확인 못 해(U87), 가입 실패는
  일반화된 안내 문구로 보여준다 — 위 사전 검사가 흔한 케이스는 이미 걸러준다.

### 팀 관리 화면 (`#/team`, `TeamRoute.tsx`)

- 목록 화면(LIST) 우하단에 `팀 관리` 버튼을 추가했다.
- 팀장이면: 초대코드 만들기(만료일 선택 입력) + 발급된 코드 목록(사용횟수·만료일·취소 버튼).
  코드를 누르면 클립보드로 복사된다.
- 팀원이면: "초대코드 발급·취소는 팀장만 할 수 있습니다" 안내만 보인다(실제 방어는 RLS).

## 어떻게 확인하나

**0. 먼저 마이그레이션을 실 프로젝트에 적용해야 한다** — Supabase 대시보드 SQL Editor 에서
`supabase/migrations/20260908000000_invite_codes.sql` 전체를 실행(몇 번 실행해도 안전).

1. 기존 팀장 계정으로 로그인 → 목록 화면 우하단 `팀 관리` 클릭 → `초대코드 만들기` →
   코드가 목록에 뜨는지, 복사 버튼이 동작하는지.
2. 그 코드를 들고 로그아웃 상태(시크릿창)에서 로그인 화면 → `초대코드로 가입` → 새 이메일·
   비밀번호·방금 만든 코드로 가입 → (이메일 확인이 꺼져 있으면) 바로 로그인되고, 목록에
   팀장과 같은 용역들이 보이는지.
3. 잘못된 코드(예: 마지막 글자를 하나 바꿔서)로 가입을 시도 → 가입이 거부되고 안내 문구가
   뜨는지 (Supabase Auth 대시보드에 그 이메일로 계정이 남지 않는지도 같이 확인해 주시면
   좋습니다 — 트리거 롤백이 실제로 되는지의 핵심 증거입니다).
4. 팀장 화면에서 그 코드를 `취소` → 취소된 코드로 다시 가입 시도 → 거부되는지.
5. 팀원(MEMBER) 계정으로 로그인해 `팀 관리`에 들어가면 발급 화면이 아니라 안내 문구만
   보이는지.

## 이렇게 가정하고 만들었습니다

`_workspace/ASSUMPTIONS.md` U86~U90 전문:

- **U86** 가입 폼은 이메일+비밀번호+초대코드 3개뿐 — `login_id`/`display_name` 은 이메일에서
  자동 생성(화면에 안 쓰이는 내부 필드라 사용자에게 따로 안 물었다).
- **U87** 트리거 예외의 원문이 클라이언트까지 오는지 확인 못 함 — 사전 검사(RPC)로 흔한
  케이스를 걸러내고, 나머지는 일반화된 안내 문구로 처리.
- **U88** 이메일 확인 on/off 를 몰라 양쪽 다 되게 짰다(세션 있으면 즉시 로그인, 없으면 안내).
- **U89** `#/team` 화면은 방문하면 곧바로 초대코드 목록을 불러온다 — 규칙 0(자동 동기화
  없음)은 용역 데이터에 대한 것이지 팀 관리 화면 조회는 대상이 아니라고 판단.
- **U90** 초대코드 발급 UI 에 인원수 제한(`max_uses`) 입력란은 안 만들었다 — D54 는 "다회용
  +만료일"만 요구했다. 컬럼은 스키마에 있으니 필요하면 입력란만 추가하면 된다.

## 남은 것 / 못 한 것

- 위 5개 시나리오 전부 실 Supabase 프로젝트에서 확인 대기(에이전트는 브라우저도, 대시보드도
  띄우지 않는다는 하네스 규칙 + 이 세션엔 접근 정보 자체가 없다).
- 가입 폼에 "이 코드는 ○○팀 코드입니다" 같은 사전 확인(팀 이름 미리보기)은 안 만들었다 —
  `check_invite_code` 가 팀 이름을 이미 돌려주긴 하지만, 화면에서 쓰지 않고 유효성 확인
  용도로만 썼다. 필요하면 폼에 한 줄 추가하는 정도로 가능하다.
- 팀장 본인이 팀장 자리를 넘기거나(OWNER 승계), 팀원을 팀에서 제외하는 기능은 이번 범위 밖.
