## 1. 구현 가능 판정

### 판정: **조건부 가능 — S3-T1 부터 지금 착수 가능**

| | 내용 |
|---|---|
| **차단 질문** | **0건** |
| **비차단 질문** | **7건 (Q17~Q23)** — 전부 이 문서에 기본값을 확정했고 `ASSUMPTIONS.md` **S3·S4 · F1~F8** 에 기록했다 (자체 판단 19건은 F9~F27) |
| **IndexedDB 마이그레이션** | **없다.** S1 이 `itemSettings` 스토어(`keyPath: id`, `by_project`)를 v1 에 이미 만들어 뒀다(`data/idb/db.ts:150`). 새 스토어·새 인덱스·DB 버전 업 **0건** |
| **기존 구현을 깨는 변경** | **3곳뿐이고 전부 기계적이다** — §2-6 참조. 캔버스 렌더·히트·커맨드는 한 줄도 건드리지 않는다 |
| **S2b 로 미루는 것** | 폼의 저장 배선 · 직전 입력 기억 · 빠른입력 · Undo 병합 (§6) |

**왜 "바로 착수 가능"이 아닌가 — 세 가지 남은 불확실성**

1. **Q17(설정 편집 대상)** — 상세기획 §2-A 가 서로 배타적인 두 효과를 동시에 약속한다.
   *"이름을 고치면 전 프로젝트에 한 번에 반영"* 과 *"과업 생성 시 스냅샷 복사 → 조직 설정을 바꿔도
   이미 만든 과업은 변하지 않는다"* 는 **동시에 성립할 수 없다.** 이 문서는 스냅샷 쪽을 택했다(§2-2).
   화면 수가 1개냐 2개냐가 여기서 갈리지만, 데이터 모델은 어느 쪽이든 같고 화면은 `scope` 프롭 하나다 → **비차단**.
2. **Q18~Q19(규모 입력의 숫자 해석)** — 손상결함표에 **직접 인쇄되는 값**이라 결국 사용자 확인이 필요하다.
   다만 값 매핑은 상수표 한 곳(§3-5-c)에 모으고, 저장 필드는 이미 분리해 두므로 답이 늦어도 뒤집는 비용이 낮다 → **비차단**.
3. **Q20(씨앗 목록의 도메인 정확성)** — 부재의 구조체/비구조체 판정은 안전진단 실무 지식이다.
   씨앗은 **설정 화면에서 전부 수정 가능**하고 기존 결함에 영향이 없으므로(§2-5-e) → **비차단**.

**왜 "착수 불가"가 아닌가**

가장 위험했던 지점 — *"과업 스냅샷을 넣으려면 이미 만들어진 용역을 어떻게 하나"* — 는
**지연 스냅샷(§2-4)** 으로 마이그레이션 없이 해소된다. `itemSettings` 가 이미 비어 있는 채로 존재하고,
결함 속성은 이름 스냅샷을 함께 저장하므로(§3-2) 설정이 없어도 기존 결함이 깨지지 않는다.

### 2-1. 저장 구조 — `itemSettings` 스토어 하나, **문서 1건 = 설정 1벌**

> **결론: 스토어를 새로 만들지 않는다. `itemSettings` 안에 넣는다. 마이그레이션 0.**

`itemSettings` 는 `keyPath: 'id'`, 인덱스 `by_project(projectId)` 로 **v1 에 이미 생성돼 있다.**
여기에 **문서 단위**로 넣는다 — 레코드 1건이 설정 한 벌 전체다.

```
itemSettings
├─ id: 'ORG'        scope: 'ORG'      projectId: null   ← 마스터 (새 용역의 초기값)
├─ id: '{projectId}' scope: 'PROJECT'  projectId: '{...}' ← 과업 스냅샷 (불변식 #7)
└─ …용역 수만큼
```

- 읽기는 **항상 기본키 `id`** 로 한다. `by_project` 인덱스는 쓰지 않는다.
  (IndexedDB 는 keyPath 값이 유효한 키가 아니면 — `null` 포함 — 그 레코드를 인덱스에 넣지 않고 **예외도 던지지 않는다.**
  따라서 `ORG` 문서는 `by_project` 에서 자연히 빠진다. 이 동작에 의존하지 않기 위해 인덱스를 아예 안 쓴다.)
- 삭제: 용역 하드 삭제 시 같은 트랜잭션에서 `itemSettings[projectId]` 도 지운다.
  (용역은 소프트 삭제이므로 실제 삭제는 Phase 5 — 지금은 남겨 둔다.)

#### 2-1-a. 왜 "행 단위"가 아니라 "문서 단위"인가

| 안 | 판정 |
|---|---|
| 행 단위 (마스터 1건 = 레코드 1건, 링크 1건 = 레코드 1건) | **탈락.** 드래그 재정렬 한 번이 링크 수십 건의 `sortOrder` 를 동시에 쓴다. 트랜잭션 하나에 묶어도 부분 상태가 눈에 보이고, `kind` 판별자로 8종을 한 스토어에 섞으면 인덱스 하나로는 못 뽑는다 |
| **문서 단위 (채택)** | 설정은 **항상 통째로 읽고 통째로 쓴다.** 폼도 전체 트리를 필요로 한다. 쓰기가 `put` 1회라 원자적이고 부분 상태가 없다 |
| 문서 안을 **중첩(nested)** 으로 | **탈락.** `부재 > 결함유형 > 원인` 으로 중첩하면 **함정 #4 를 저장 형식에서 재현**한다. "건조수축"이 13벌 생긴다 |

**채택안의 정확한 형태 — 문서 안은 정규화(마스터 배열 + 링크 배열)를 유지한다.**
저장 단위만 문서일 뿐, 구조는 상세기획 §2-A 의 마스터+연결 그대로다.

크기 추정: 마스터 ≈ 40건, 링크 ≈ 900건, 항목당 100B 이하 → **문서 1건 ≈ 100KB 미만.** 문제 없다.

**Phase 5 인계**: 항목마다 `updatedAt` 을 갖고 있으므로, 나중에 행 단위 병합이 필요해지면
**저장 입도만 바꾸면 되고 형식은 그대로다.** 지금 행 단위로 쪼개서 얻을 것이 없다.

### 2-2. 타입 확정 — `packages/project-core/src/items/`

새 패키지를 만들지 않는다. `project-core` 안의 하위 폴더다 (순수 TS · RN 재사용 · `canvas-core` 를 import 하지 않는다).

```ts
// packages/project-core/src/items/types.ts

export type StructureType = 'RC' | 'SRC' | 'SS';
export type Structural    = 'STRUCTURAL' | 'NON_STRUCTURAL';   // 구조체 / 비구조체
export type SizeMode      = 'WL' | 'AREA';                     // 폭×길이 / 면적

type MasterBase = { id: string; name: string; createdAt: number; updatedAt: number };

export type MemberMaster     = MasterBase & { structural: Structural };
export type DefectTypeMaster = MasterBase & { defaultSizeMode: SizeMode };
export type CauseMaster      = MasterBase & { code: number };   // 손상결함표 숫자 코드 (§2-5-d)
export type RepairMaster     = MasterBase;

export type LinkStructureMember = {
  structureType: StructureType; memberId: string; favorite: boolean; sortOrder: number;
};
export type LinkMemberDefectType = {
  memberId: string; defectTypeId: string;
  /** **이 (부재, 결함유형) 조합의 규모모드.** 마스터 기본값은 링크를 만들 때의 초기값일 뿐이다 */
  sizeMode: SizeMode;
  favorite: boolean; sortOrder: number;
};
export type LinkDefectTypeCause  = { defectTypeId: string; causeId: string;  isDefault: boolean; sortOrder: number };
export type LinkDefectTypeRepair = { defectTypeId: string; repairId: string; isDefault: boolean; sortOrder: number };

export type ItemSettings = {
  id: string;                       // 'ORG' | projectId
  scope: 'ORG' | 'PROJECT';
  projectId: string | null;         // ORG 이면 null
  settingsVersion: number;          // 문서 내부 형식 버전. 현재 1. **DB schemaVersion 과 별개**
  /** 스냅샷을 뜬 시점의 ORG.updatedAt. null = ORG 문서 자신 */
  snapshotFrom: number | null;

  members: MemberMaster[];
  defectTypes: DefectTypeMaster[];
  causes: CauseMaster[];
  repairs: RepairMaster[];

  linkStructureMember: LinkStructureMember[];
  linkMemberDefectType: LinkMemberDefectType[];
  linkDefectTypeCause: LinkDefectTypeCause[];
  linkDefectTypeRepair: LinkDefectTypeRepair[];

  createdAt: number; updatedAt: number; deviceId: string; createdBy: string | null;  // RecordBase
};
```

> **`LinkMemberDefectType` 에 `structureType` 이 없는 것은 의도다** (상세기획 §2-A 표와 동일).
> 부재 `벽(구조체)` 가 RC 와 SRC 양쪽에 연결돼 있으면, 두 탭에서 **같은 결함유형 목록**을 본다.
> 구조유형마다 다른 결함유형을 주고 싶으면 부재를 분리해야 한다 — 그것이 실무 표기와도 맞는다.

**`sortOrder` 는 S1 의 층 정렬과 같은 `STEP = 10` 격자**를 쓴다(`floorOrder.ts` 의 `reorder`/`renumber` 규칙 재사용).
음수 규약은 여기서 필요 없다 — 지하 개념이 없다.

### 2-3. 접점 계층 — `resolve.ts` (**S3 와 S4 를 잇는 유일한 API**)

폼은 `ItemSettings` 의 링크 배열을 직접 훑지 않는다. 아래 순수 함수만 부른다.
S3 이 저장 구조를 바꿔도 S4 는 이 시그니처만 보면 된다.

```ts
// packages/project-core/src/items/resolve.ts

export type MemberOption     = { id: string; name: string; structural: Structural; favorite: boolean };
export type DefectTypeOption = { id: string; name: string; sizeMode: SizeMode;     favorite: boolean };
export type CauseOption      = { id: string; name: string; code: number; isDefault: boolean };
export type RepairOption     = { id: string; name: string;                isDefault: boolean };

/** 정렬 = sortOrder 오름차순. 즐겨찾기는 정렬을 바꾸지 않는다 (§2-5-b) */
export function membersOf(s: ItemSettings, st: StructureType): MemberOption[];
export function defectTypesOf(s: ItemSettings, memberId: string): DefectTypeOption[];
export function causesOf(s: ItemSettings, defectTypeId: string): CauseOption[];
export function repairsOf(s: ItemSettings, defectTypeId: string): RepairOption[];

/** 결함유형별 기본 원인·보수방안. 없으면 null */
export function defaultCauseOf(s: ItemSettings, defectTypeId: string): CauseOption | null;
export function defaultRepairOf(s: ItemSettings, defectTypeId: string): RepairOption | null;
```

### 2-4. 과업 스냅샷과 **이미 만들어진 용역** (불변식 #7)

> **결정: 지연 스냅샷(lazy). 일괄 마이그레이션을 돌리지 않는다.**

| 상황 | 동작 |
|---|---|
| DB 를 열 때 `itemSettings['ORG']` 가 없다 | 씨앗(§2-7)으로 **1회 생성**한다 |
| **새 용역 생성** (S3 이후) | 그 트랜잭션에서 `ORG` 를 복사해 `itemSettings[projectId]` 를 만든다 (`snapshotFrom = ORG.updatedAt`) |
| **이미 있는 용역** (S1·S2a 로 만든 것) 을 처음 열 때 | `itemSettings[projectId]` 가 없으면 **그 시점의 ORG 를 복사해 만들고 저장**한다. 사용자에게는 아무것도 묻지 않는다 |
| 스냅샷이 있는 용역 | ORG 가 나중에 바뀌어도 **절대 자동 반영하지 않는다** |

**왜 지연인가**
- DB 버전을 올리지 않아도 된다 → 마이그레이션 경로가 늘지 않는다 (S1 §2-9-e 의 `migrations[]` 를 건드리지 않는다).
- 용역이 100개여도 여는 것만 만든다.
- **약점**: S3 이전에 만든 용역은 "생성 시점"이 아니라 "처음 여는 시점"의 ORG 를 받는다.
  씨앗 직후에는 ORG 가 한 벌뿐이라 실질 차이가 없다. → **Q23 (비차단, F5)**

**진입 지점은 한 곳으로 모은다**: `repo.ensureProjectSettings(projectId): Promise<ItemSettings>`.
설정 화면·결함 입력 폼·(나중의) 출력이 전부 이 함수만 부른다. 호출자가 "없으면 만든다"를 각자 구현하면 반드시 어긋난다.

| 규칙 | 값 |
|---|---|
| 선택 상태 | 컬럼1 선택 → 컬럼2 갱신, 컬럼2 선택 → 컬럼3 갱신. **탭을 바꾸면 컬럼1 선택은 그 탭의 첫 항목으로 초기화** |
| 빈 상태 | 컬럼2: `왼쪽에서 부재를 선택하세요` / 컬럼3: `가운데에서 결함유형을 선택하세요` |
| 목록이 비었을 때 | `아직 등록된 항목이 없습니다. 위 입력창에서 추가하세요.` + `[기본 항목 세트 불러오기]` |
| 카운트 | **`항목 17 · ★ 17`** 로 쓴다. 젠트릭스의 `자주 사용하는 항목 17` 은 즐겨찾기 개수가 아니라 전체 개수여서 오독을 부른다 (→ §5 지적) |

| ★ 가 정렬에 미치는 영향 | **없다.** 정렬은 `sortOrder` 하나뿐이다. 즐겨찾기가 순서까지 바꾸면 드래그로 맞춘 순서가 무의미해진다 |
| 드래그 | `⠿` 핸들. 드롭 시 그 링크 목록의 `sortOrder` 를 STEP=10 격자로 재부여 (S1 `reorder()` 재사용) |

#### 2-5-c. `[추가]` 의 동작 — **함정 #4 를 실제로 막는 지점**

```
addItem(name):
  1. 이름 정규화 (trim, 연속 공백 1개로)
  2. 이 목록(링크)에 같은 이름이 이미 있다  → 거부 + 흔들림 애니메이션 + `이미 이 목록에 있습니다`
  3. 마스터에 같은 이름이 있다              → **마스터를 만들지 않고 링크만 추가**
                                              토스트: `'건조수축' 은 이미 등록된 항목입니다. 이 결함유형에 연결했습니다.`
  4. 그 외                                  → 마스터 생성 + 링크 생성
```

3번이 없으면 `건조수축` 이 결함유형 13개마다 별개 마스터로 생기고 **코드번호가 13개**가 된다.
이름 비교는 정규화 후 **대소문자·공백 무시** 로 한다.

#### 2-5-d. 삭제 — 링크 삭제와 마스터 삭제를 UI 에서 반드시 구분한다

| 조작 | 위치 | 결과 |
|---|---|---|
| **이 목록에서 빼기** | 행 `⋯` 메뉴 · 발생원인/보수방안 열은 `🗑` | 링크 1건만 삭제. 마스터와 다른 연결은 그대로 |
| **마스터에서 완전히 삭제** | `⋯` 메뉴 하단 (구분선 아래, 위험 색) | 마스터 + 그 마스터를 가리키는 **모든 링크** 삭제 |

마스터 삭제 확인 다이얼로그는 **실측 건수를 넣는다**:
> `'건조수축' 을 완전히 삭제합니다.`
> `결함유형 8개의 발생원인 목록에서 사라집니다.`
> `이미 입력된 결함 12건은 그대로 유지됩니다 (기록된 이름이 남습니다).`

**마지막 줄이 이 설계의 핵심 안전장치다** — 결함은 `causeId` 와 `causeName` 을 **둘 다** 저장하므로(§3-2),
설정을 지워도 이미 작성된 보고서 데이터가 깨지지 않는다.

기본값으로 지정된 항목을 빼면 → 남은 목록의 **첫 항목**이 자동으로 기본값이 된다. 목록이 비면 기본값 없음.

#### 2-5-e. 설정 변경이 기존 결함에 미치는 영향 — **없다**

| 설정 조작 | 이미 입력된 결함 |
|---|---|
| 항목 이름 변경 | **바뀌지 않는다.** 결함에 이름이 스냅샷돼 있다 |
| 항목 삭제 | **바뀌지 않는다.** `id` 가 가리키는 대상이 사라져도 이름으로 표시·출력된다 |
| 규모모드 변경 | **바뀌지 않는다.** `sizeMode` 는 결함마다 저장된다 |
| 발생원인 코드번호 변경 | **출력에서 바뀐다.** 코드는 `causeId` 로 조회하는 값이다 (→ Q21) |

#### 2-5-f. 발생원인 코드번호

- `CauseMaster.code` — 정수, **문서 안에서 유일**. 새 원인 추가 시 `max(code) + 1`.
- 컬럼3 각 행 앞에 배지로 노출한다(`① 건조수축`). 사용자가 직접 편집 가능(중복이면 거부).
- **출력의 `발생원인 추정` 열은 이 코드를 그대로 쓴다.** 같은 데이터에서 항상 같은 숫자가 나온다(출력 재현성).
- 보고서마다 등장한 원인만 1..n 으로 다시 매기는 관행이 있다면 그것은 **출력 파라미터**이고
  `ExportRun` 스냅샷 대상이다 → Phase 4. **지금 코드를 계산값으로 만들지 않는다** (→ Q21, §5 지적).

### 3-2. `DefectAttrs` — canvas-core `Defect` 에 합성

```ts
// packages/canvas-core/src/types.ts

/**
 * 결함의 **도메인 속성**. canvas-core 는 이 값을 해석하지 않는다
 * (유일한 예외: completeness.ts 의 필수항목 판정).
 * 렌더·히트·커맨드는 이 타입을 전혀 모른다.
 */
export type DefectAttrs = {
  // ── 분류 ──────────────────────────────────────────────
  surveyKind: 'EXTERIOR' | 'DETAIL';        // 외관조사 / 정밀점검. 폼 미노출, 기본 EXTERIOR
  locationNote: string | null;              // 위치보조 (거실 · 복도 · 계단실)
  structureType: 'RC' | 'SRC' | 'SS' | null;

  memberId: string | null;                  // ← 신규
  memberName: string | null;                // (기존) 출력·표시에 쓰는 **이름 스냅샷**
  /** null = 부재 마스터의 구조체 구분을 그대로 쓴다. 값이 있으면 사용자가 손댄 것 */
  structural: 'STRUCTURAL' | 'NON_STRUCTURAL' | null;   // ← 신규

  defectTypeId: string | null;              // ← 신규
  defectTypeName: string | null;            // (기존)

  // ── 규모 (§3-5) ───────────────────────────────────────
  sizeMode: 'WL' | 'AREA';                  // ← 신규. 기본 'WL'
  widthMm: number | null;                   // (기존) WL 전용
  lengthMm: number | null;                  // (기존) WL 전용
  areaM2: number | null;                    // (기존) AREA 전용 — **직접 입력값**
  areaWMm: number | null;                   // ← 신규. AREA 의 가로 (보조 입력)
  areaHMm: number | null;                   // ← 신규. AREA 의 세로 (보조 입력)
  countEa: number | null;                   // (기존) null 은 1 로 읽는다

  // ── 판정 ──────────────────────────────────────────────
  progress: 'NONE' | 'ONGOING';             // ← 신규. 진행 없음 / 진행 중
  leak: boolean;                            // ← 신규. 누수여부 O/X

  causeId: string | null;                   // ← 신규
  causeName: string | null;                 // ← 신규. 자유 텍스트면 id=null, name 만 채운다
  repairId: string | null;                  // ← 신규
  repairName: string | null;                // ← 신규

  memo: string | null;                      // (기존)
};

export type Defect = {
  id: string; projectId: string; drawingId: string; floorId: string;
  seq: number; status: DefectStatus;
  marks: Mark[]; label: Label; sketch: SketchPath[]; style: StyleOverride | null;
} & DefectAttrs;

export const EMPTY_DEFECT_ATTRS: DefectAttrs = { /* 전부 null / 'WL' / 'NONE' / false / 'EXTERIOR' */ };
```

**`id` 와 `name` 을 둘 다 저장하는 이유**

| 필요 | 어느 쪽이 답하나 |
|---|---|
| 보고서에 인쇄할 글자 | **`name`** — 설정이 바뀌어도 이미 쓴 보고서 용어가 흔들리지 않는다 (스냅샷 원칙) |
| 발생원인 코드번호 조회 | **`id`** — 이름으로는 못 찾는다 |
| 항목을 삭제한 뒤에도 결함이 살아 있어야 함 | **`name`** (§2-5-e) |
| 통계·역참조·"이 부재의 결함 몇 건" | **`id`** |

상세기획 §3-3 `발생원인 | ref | text | 코드번호·텍스트 둘 다 지원` 과 정합한다.

### 3-4. 미완성 판정 — 손대지 않는다

### 3-5. **규모 — 사용자의 "넓이×높이" 를 어떻게 다루는가** ⚠️

> **사용자 표현**: *"균열 폭×길이 또는 넓이×높이"*
> **상세기획 §2-B**: `AREA` 모드 안에 `[가로×세로로 입력] ← 누르면 가로·세로 입력 후 자동계산`
> **상세기획 §3-6**: `면적 = (폭mm ÷ 1000) × (길이mm ÷ 1000)`, 소수 4자리 절사, **개소는 곱하지 않는다**

#### 3-5-a. 확정: 모드는 **2종 유지**, 가로×세로는 AREA 안의 **보조 입력**

세 번째 모드를 만들지 않는다. 이유:
- 설정 화면의 라디오가 2개다(젠트릭스 실측 · 상세기획 §2-A 토글).
- 손상결함표 열은 `폭(mm) · 길이(mm) · 면적(㎡) · 개소(EA)` **4개로 고정**돼 있다.
  모드를 3개로 늘려도 실을 자리가 없다.
- 그리고 결정적으로, **WL 과 가로×세로는 계산식이 완전히 같다.** 라벨과 출력 표기만 다르다.

```
규모 섹션 헤더:  규모   [ 폭 × 길이 | 면적 ]   ← 현장에서 그 자리에서 바꾼다

── sizeMode = 'WL' ───────────────────────
   폭    − [ 0.2 ] mm +      구간 프리셋 6
   길이  − [ 300 ] mm +      값 프리셋 15
   개소  − [ 2 ] 개 +        1~10
   면적  0.0006 ㎡  ← **읽기 전용 파생값.** 입력칸이 아니다

── sizeMode = 'AREA' ─────────────────────
   면적  − [ 0.5 ] ㎡ +      프리셋 8
   개소  − [ 1 ] 개 +
   [ 가로 × 세로로 계산 ]   ← 펼치면
        가로 − [ 1000 ] mm +   세로 − [ 500 ] mm +
        → 면적 0.5 ㎡ 로 자동 계산되어 위 칸에 들어간다
```

#### 3-5-b. 저장 규칙

| 모드 | 저장하는 것 | 저장하지 않는 것 |
|---|---|---|
| `WL` | `widthMm`, `lengthMm` | **`areaM2` — 파생값이므로 저장하지 않는다** (함정 #1: 계산할 수 있는 것은 저장하지 않는다) |
| `AREA` (직접) | `areaM2` | `widthMm`, `lengthMm`, `areaWMm`, `areaHMm` = null |
| `AREA` (가로×세로) | `areaM2` (계산 결과) **+ `areaWMm`, `areaHMm`** | `widthMm`, `lengthMm` = null |

가로·세로를 저장하는 이유: 나중에 "세로만 고치고 싶다"가 가능해야 한다. 저장 안 하면 재편집 시 사라진다.

**모드를 전환해도 반대편 값을 지우지 않는다.** 되돌아오면 그대로 복원된다.
실수로 전환해 입력값을 잃는 것이 가장 나쁘다. 출력은 **현재 `sizeMode` 만** 본다.

#### 3-5-c. 계산 — `packages/project-core/src/items/size.ts`

```ts
/** 소수 4자리 **절사**(반올림 아님). 부동소수 잡음 방지용 ε 를 더한다 */
export function trunc4(m2: number): number {
  return Math.trunc(m2 * 1e4 + 1e-9) / 1e4;
}

/** §3-6. 두 mm 값의 면적(㎡). **mm² 로 곱한 뒤 나눈다** — 0.0001 × 2.5 처럼 미리 나누면 오차가 커진다 */
export function areaFromMm(aMm: number, bMm: number): number {
  return trunc4((aMm * bMm) / 1e6);
}

/** 표시·출력이 쓰는 실효 면적. WL 이면 파생, AREA 면 저장값 */
export function effectiveAreaM2(a: DefectAttrs): number | null;

/** 손상결함표 4열. **개소는 어디에도 곱하지 않는다** (§3-6 실측: 개소 2인데 면적 0.0004) */
export function outputSize(a: DefectAttrs): { widthMm: number; lengthMm: number; areaM2: number; countEa: number };
```

§3-6 실측 검증표 4행을 **그대로 단위테스트로 고정한다**:

| 폭 | 길이 | 기대값 |
|---|---|---|
| 0.2 | 2000 | `0.0004` |
| 0.1 | 2500 | `0.0002` (절사 — 반올림이면 0.0003 이 되어 틀린다) |
| 0.2 | 4000 | `0.0008` |
| 200 | 300 | `0.06` |

`outputSize` 에서 `sizeMode='AREA'` 일 때 폭·길이는 **`0`** 으로 낸다 (실측 누수흔적 행 `0 / 0 / 0.5`).
가로×세로로 입력한 경우도 마찬가지로 `0` 이다 → **Q19** (F11).

#### 3-5-d. 프리셋 값표 (한 파일에 모은다 — `items/presets.ts`)

| 항목 | 프리셋 | 스테퍼 |
|---|---|---|
| **폭(mm)** | `~0.1mm미만` `0.1~0.2mm` `0.2~0.3mm` `0.3~0.5mm` `0.5mm이상` `직접입력` (2열×3행) | ±0.1 |
| **길이(mm)** | 100 200 300 400 500 600 700 800 900 1000 1200 1500 1800 2000 3000 (5열×3행) | ±100 |
| **개소(EA)** | 1~10 (5열×2행) | ±1 |
| **면적(㎡)** | 0.1 0.25 0.5 1 2 3 5 10 (4열×2행) | ±0.1 |
| **가로·세로(mm)** | 길이와 같은 15종 | ±100 |

**폭 구간 버튼이 넣는 숫자** (→ **Q18**, 기본값 = 구간 상한):

| 버튼 | 저장 숫자 |
|---|---|
| `~0.1mm미만` | 0.1 |
| `0.1~0.2mm` | 0.2 |
| `0.2~0.3mm` | 0.3 |
| `0.3~0.5mm` | 0.5 |
| `0.5mm이상` | **직접입력 모드로 전환하고 0.5 를 초기값으로 넣는다** (0.3~0.5 와 같은 숫자가 되면 안 된다) |
| `직접입력` | 스테퍼·키보드 입력 활성 |

- 헤더 우측에 **현재 선택한 구간 라벨**을 그대로 보여준다(실측 `0.1mm이상~0.2mm미만`).
  숫자만 보이면 사용자가 어느 구간을 눌렀는지 잊는다.
- 라벨과 숫자의 대응이 실무 관행과 다르면 이 표 한 곳만 고치면 된다.

### 3-6. 값 연동 규칙 (**사용자가 보게 될 동작이므로 전부 명시한다**)

| 조작 | 결과 |
|---|---|
| **구조유형을 바꾼다** | 부재 목록이 갈린다. 현재 부재가 새 목록에 없으면 **부재·결함유형·원인·보수방안을 비운다** + 안내 `이 구조유형에는 '{부재}' 가 없어 선택을 해제했습니다` |
| **부재를 바꾼다** | ① `structural` 을 **새 부재의 기본값으로 되돌린다**(수동 표시 해제) ② 결함유형 목록이 갈린다. 현재 결함유형이 새 목록에 있으면 **유지**, 없으면 비운다 |
| **결함유형을 바꾼다** | ① `sizeMode` ← 그 (부재, 결함유형) 링크의 값 ② 원인·보수방안: 현재 값이 새 목록에 있으면 **유지**, 없으면 **새 기본값**으로 교체 ③ **규모 숫자는 유지한다**(모드가 그대로면) |
| **구조체 여부를 손으로 누른다** | `structural` 에 값이 박힌다. 세그먼트 옆 라벨이 `부재 기본값` → `직접 지정` 으로 바뀐다 |
| **모드를 바꾼다** | 반대편 값은 보존 (§3-5-b) |

> **부재를 바꾸면 구조체 구분이 되돌아가는 것**은 의도된 동작이다.
> 부재가 바뀌면 이전 수동 선택의 근거가 사라진다. 조용히 틀린 값이 보고서에 남는 것이 더 나쁘다.
