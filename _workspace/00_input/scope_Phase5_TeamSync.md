# 범위 — Phase 5 착수: 팀 동기화 서버 + 로그인, 오프라인 설치형 태블릿 UI

날짜: 2026-09-02. 사용자 원문 요청 + 리더가 즉석에서 받은 블로킹 질문 답변.

## 1. 동기화 서버 + 로그인 (사용자 원문)

> 로그인시 사용자(팀원) (팀)이 있어야해.
> 같은 팀은 프로젝트가 동기화. 단, 현장에서 진행 중일 때는 동기화 안함
> (사무실 복귀 후 동기화 진행)(프로젝트별 동기화 별도버튼 구현)
> 팀에는 팀장1인과 팀원(다수)로 구성

**리더가 즉석에서 물은 블로킹 질문 2건 (AskUserQuestion) — 답변 완료:**

| 질문 | 답변 |
|---|---|
| 서버(백엔드+DB) 어디에? | **Vercel 서버리스 함수 + 매니지드 DB** (VPS 직접 구축·기존 인프라 아님) |
| 팀원 로그인 발급 방식? | **팀장이 아이디·비번을 직접 발급** (이메일 가입도, 소셜 로그인도 아님) |

**리더가 계속 진행하며 정할 것(비차단, 스펙 단계에서 구체화):**
- 매니지드 DB 벤더 — Supabase 권장(Postgres + 내장 Auth로 비밀번호 해싱·세션 발급을 직접
  구현하지 않아도 됨. "팀장이 직접 발급"은 Supabase Auth의 admin API로 구현 가능). Neon 등
  대안도 검토는 하되, 보안에 민감한 인증 코드를 직접 짜지 않는 쪽을 우선한다
- 동기화 단위·충돌 해결 — `RecordBase.updatedAt`/`deviceId`가 이미 예약돼 있음(D5). LWW(최종
  수정 우선) 병합을 기본으로 검토
- "프로젝트별 동기화 버튼"의 정확한 UX(어디 있는지, 진행 중 표시, 실패 시 재시도)
- 팀장/팀원 권한 차이 — 팀 관리(팀원 초대·해제)는 팀장만. 팀 내 프로젝트 가시성은 팀원 전체
  동일(현재 사용자 원문에서 프로젝트별 세부 접근제어 언급 없음 — 확인 필요하면 QUESTIONS.md)

**기존에 이미 있는 관련 결정 — 뒤집지 말 것:**
- D5: `RecordBase.updatedAt`/`deviceId` 필드 예약 이미 존재 — Phase 5 병합의 재료
- D12(Q40): "자체 서버 구축(과업 단위 push-pull 동기화)" 확정 — 이번 요청이 그 구체화다.
  파일 번들 수동 왕복은 채택 안 됨
- `RecordBase.createdBy: string | null` — "사용자 개념은 Phase 5. S1은 null" — 이제 이 필드를
  실제로 채울 시점이다
- `Project.orgId: string | null` — "조직은 Phase 5. 지금은 null" — 이번 팀 개념과의 관계 정리 필요
  (조직=회사, 팀=조직 하위 단위인지, 아니면 팀=조직과 동급인지 스펙에서 정한다)

**기존에 이미 있는 관련 결정 — 뒤집지 말 것:**
