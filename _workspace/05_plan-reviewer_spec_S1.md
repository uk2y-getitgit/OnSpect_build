## 1. 구현 가능 판정

### 판정: **조건부 가능**

| | 내용 |
|---|---|
| **차단 질문** | **0건** |
| **비차단 질문** | **3건 (Q13~Q15)** — 전부 이 문서에 기본값을 확정했고 `ASSUMPTIONS.md` S1 · D1~D14 에 기록했다 |
| **사용자 확정** | **D4**(구현 순서 `S1→S2a→S3→S4→S2b→S5`) · **D5**(IndexedDB 영속 저장) 를 반영했다. 내가 올리려던 저장 질문은 **D5 로 이미 답이 왔다** |
| **builder 착수** | **S1-T1 부터 지금 시작 가능.** T13(PDF)만 Q13 답 대기로 세워 둔다 |

**왜 "착수 불가"가 아닌가 — PDF 판단의 근거**

PDF 지원은 겉보기에 아키텍처 결정이지만, **인입 파이프라인을 아래처럼 자르면 순수 가산(加算)이 된다.**

```
UploadSource(파일 N개) ──▶ PageCandidate[] ──▶ [층 배정 화면] ──▶ Drawing[]
                              ▲                     ▲
                  imageIngest.ts (S1)         이 화면은 두 경로가 공유한다
                  pdfIngest.ts  (후속)
```

`PageCandidate = { key, renderBlob, thumbBlob, imageWidth, imageHeight, sourceLabel }` 로 통일하면
이미지 1파일 = 후보 1개, PDF 1파일 = 후보 N개일 뿐이고 **뒤쪽 화면·모델·저장은 한 벌**이다.
`Drawing.source` 를 `{kind:'IMAGE'} | {kind:'PDF_PAGE'}` 유니온으로 **지금 미리 정의**하므로
나중에 `pdf.js` 를 넣어도 마이그레이션이 없다. → **비차단.**

**왜 "바로 착수 가능"이 아닌가**

Q13(PDF)은 *"사용자의 실제 도면이 PDF뿐이면 S1의 테스트 목적 자체가 반쯤만 달성된다"* 는 위험을 안는다.
구조를 굳히지는 않으므로 기본값(이미지 전용)으로 진행하되, **답이 오면 T13 을 앞으로 당긴다.**
Q14·Q15 는 폼 필드와 UI 제약이라 뒤집는 비용이 낮다.

**D5 로 해소된 것**

저장은 원래 이 문서의 최대 미결이었다 — 메모리만 두면 새로고침에 도면이 사라져 S1 의 존재 이유가 무너지고,
IndexedDB 를 쓰면 Phase 5 영역을 앞당기게 된다. **D5 가 후자를 명시적으로 승인했고,
"버리는 작업이 아니다 · Phase 5 가 이어받는다" 는 조건을 달았다.** 그래서 §2-9 는
단순한 임시 저장이 아니라 **Phase 5 가 인계 가능한 스키마**로 설계했다(§2-9-e).

### 2-1. 용어 — UI 는 "용역", 코드는 `Project`

| 개념 | UI 표기 (사용자 용어) | 코드 식별자 | 상세기획 표기 |
|---|---|---|---|
| 1회차 = 1계약 | **용역** | `Project` / `projectId` | 과업 · 프로젝트 |
| 동 | **동** | `Building` / `buildingId` | 동 |
| 층 | **층** | `Floor` / `floorId` | 층 |
| 도면 | **도면** | `Drawing` / `drawingId` | 도면 |
| 결함 | **조사항목** (좌측 리스트) / **결함** (그 외) | `Defect` | 결함 |

**규칙**
1. **코드·DB·타입 식별자는 영문 `Project` 로 통일한다.** 상세기획 §3-1 이 `Project` 이고 canvas-core 가 이미 `projectId`·`floorId` 어휘를 쓴다. 여기서 `Service`/`Yongyeok` 으로 갈아타면 두 어휘가 공존한다.
2. **화면에 보이는 한국어는 전부 "용역"** 이다. "과업"·"프로젝트"는 UI 문자열에 등장하지 않는다.
3. **i18n 레이어를 도입하지 않는다.** 한국어 문자열은 컴포넌트에 직접 쓴다. 1차는 한국어 단일 로케일이다.
4. 상세기획 본문의 "과업"은 이 매핑표로 읽는다. 문서를 고치지 않는다.

### 2-4. 데이터 모델 확정

새 순수 TS 패키지 **`packages/project-core`** 에 둔다. 근거는 D1 과 동일하다 —
RN 이 그대로 재사용하고, 저장소 구현(IndexedDB → SQLite)만 갈아끼운다.
**`packages/canvas-core` 는 이 패키지를 import 하지 않는다** (역방향도 금지). 두 코어는 서로를 모른다.

```ts
// packages/project-core/src/types.ts

export type InspectionHalf = 'H1' | 'H2';                       // 상반기 | 하반기
export type InspectionKind = 'REGULAR' | 'DETAILED' | 'PRECISE';
//                            정기안전점검 | 정밀안전점검 | 정밀안전진단   (→ Q14: '기타' 미포함)

export type Project = {
  id: string;                        // uuid
  orgId: string | null;              // 조직은 Phase 5. 지금은 null
  year: number;                      // 점검연도. 정수 4자리
  half: InspectionHalf;              // 점검시기
  kind: InspectionKind;              // 점검구분
  name: string;                      // 용역명 = 상세기획 §3-1 '현장명' 자리. 예: ○○아파트 3차
  prevProjectId: string | null;      // 이전 회차 (D2). 순환 금지

  // 상세기획 §3-1 예약 필드 — S1 폼에는 없다 (→ Q14). 전부 null 로 생성된다
  clientName: string | null;         // 발주처
  periodFrom: string | null;         // YYYY-MM-DD
  periodTo: string | null;
  defaultStructureType: 'RC' | 'SRC' | 'SS' | null;

  createdAt: number;                 // epoch ms
  updatedAt: number;
  lastOpenedAt: number;              // 목록 기본 정렬 · '최근 접속' 표시
  deletedAt: number | null;          // 소프트 삭제
  schemaVersion: number;             // 현재 1
};

export type Building = {
  id: string; projectId: string;
  name: string;                      // 중축동 / 본관
  sortOrder: number;                 // 0,10,20 … 드래그 순서
  createdAt: number; updatedAt: number;
};

export type Floor = {
  id: string; projectId: string; buildingId: string;
  name: string;                      // 지하3층 · 지상1층 · 옥탑
  sortOrder: number;                 // 정수. **지하는 음수** (함정 #7). §2-7
  createdAt: number; updatedAt: number;
};

export type DrawingSource =
  | { kind: 'IMAGE';    fileName: string; mime: string; byteSize: number }
  | { kind: 'PDF_PAGE'; fileName: string; byteSize: number; pageIndex: number; pageCount: number };
  //  ↑ 예약. S1 에서는 생성되지 않지만 **지금 정의해 둔다** (§1 PDF 판단의 근거)

export type Drawing = {
  id: string; projectId: string; floorId: string;
  name: string;                      // 출력물 텍스트. 기본 `${floor.name} 결함조사 위치도`
  source: DrawingSource;
  imageWidth: number;                // 렌더이미지 픽셀. 정규화 좌표의 분모
  imageHeight: number;
  renderBlobKey: string;             // blobs 스토어 키 — 캔버스가 그리는 래스터
  sourceBlobKey: string;             // **원본 파일 Blob. 필수 (D5).** 래스터와 같은 키일 수 있다
  thumbBlobKey: string;              // 장변 320px 썸네일
  sortOrder: number;                 // 층 내 도면 순서. S1 은 항상 0 (§2-8 1:1 제한)
  createdAt: number; updatedAt: number;
};
```

> **D5 명시 사항**: `renderBlobKey`·`sourceBlobKey`·`thumbBlobKey` 는 전부 **nullable 이 아니다.**
> 도면 Blob 이 저장되지 않으면 새로고침 후 캔버스가 빈 화면이 되고, 그 순간 S1 이 실패한다.
> **원본 Blob 을 함께 보관**하는 이유는 두 가지다 — ① PDF 지원(Q13)이 켜졌을 때 원본에서 다시 렌더해야 하고,
> ② Phase 5 서버 동기화가 업로드해야 하는 것은 래스터가 아니라 원본이다.
> 이미지 입력이고 래스터화가 무손실 통과(치수 변경 없음)면 `sourceBlobKey === renderBlobKey` 로 두어 중복 저장을 피한다.

#### 2-4-a. `canvas-core` 에 가하는 유일한 변경

```ts
// packages/canvas-core/src/types.ts — Defect 에 한 줄 추가
export type Defect = {
  id: string;
  projectId: string;   // ← 추가. 상세기획 §3-3 이 요구한다
  drawingId: string;
  floorId: string;
  …
};
```

**이 한 줄 외에 canvas-core 를 건드리지 않는다** (§2-11 예외는 §2-10 의 `visibility.ts` 신규 파일 하나).
`projectId` 는 캔버스가 해석하지 않는 불투명 문자열이며, 이미 있는 `floorId` 와 성격이 같다.
저장소가 "이 용역의 결함 전부"를 인덱스로 뽑으려면 필요하다.

#### 2-4-b. 관계와 삭제 파급

| 관계 | 수 | 삭제 시 |
|---|---|---|
| Project → Building | 1 : N | Project 소프트 삭제 시 하위는 건드리지 않는다(복원 대상) |
| Building → Floor | 1 : N | Building 하드 삭제 시 하위 Floor·Drawing·Defect 도 함께 삭제. **확인 다이얼로그에 건수를 숫자로 명시** |
| Floor → Drawing | 1 : N (모델) / **1 : 1 (S1 UI)** | Floor 삭제 시 Drawing·Defect 함께 삭제 |
| Drawing → Defect | 1 : N | 도면 **교체** 는 Defect 를 지우지 않는다 (§2-8-d) |

**동·층 삭제는 Undo 스택에 들어가지 않는다.** 캔버스 Undo(`packages/canvas-core/commands.ts`)는
도면 위 편집 전용이고, 구조 삭제까지 같은 스택에 얹으면 두 화면의 되돌리기 의미가 뒤섞인다.
대신 **결함이 딸린 동·층 삭제는 확인 다이얼로그**로 막는다 (§2-11).

### 2-5. 표시명 생성 규칙

젠트릭스 실측 형식 `2025 하반기 건양대학교병원 정기안전점검` 을 그대로 채택한다.

```ts
// packages/project-core/src/displayName.ts
const HALF_LABEL: Record<InspectionHalf, string> = { H1: '상반기', H2: '하반기' };
const KIND_LABEL: Record<InspectionKind, string> = {
  REGULAR: '정기안전점검', DETAILED: '정밀안전점검', PRECISE: '정밀안전진단',
};

export function projectDisplayName(p: Project): string {
  return `${p.year} ${HALF_LABEL[p.half]} ${normalizeName(p.name)} ${KIND_LABEL[p.kind]}`;
}

/** 저장 직전 1회 적용. 앞뒤 공백 제거 + 내부 연속 공백을 1개로 접는다 */
export function normalizeName(s: string): string {
  return s.trim().replace(/\s+/g, ' ');
}
```

| 규칙 | 값 | 근거 |
|---|---|---|
| 순서 | `{연도} {시기} {용역명} {구분}` | 젠트릭스 실측 |
| 구분자 | **반각 공백 1개** | |
| **저장 여부** | **저장하지 않는다. 매번 파생한다** | 표기 규칙이 바뀌면 기존 용역 이름이 전부 옛 형식으로 굳는다. 함정 #1 과 같은 원리다 — **계산할 수 있는 것은 저장하지 않는다** |
| 예시 | `2026 상반기 ○○아파트 3차 정기안전점검` | 사용자 제시 필드값 |
| 용역명 길이 | 1~60자. 공백만은 불가 | |
| 연도 범위 | 2000 ~ 2100 정수. 기본값 = **올해** | |
| 시기 기본값 | 오늘이 1~6월이면 `H1`, 7~12월이면 `H2` | |
| 구분 기본값 | `REGULAR` (정기안전점검) | 가장 흔하다 |
| 중복 | **허용.** `(year, half, kind, name)` 이 같은 용역이 이미 있으면 저장 전 경고 `같은 이름의 용역이 이미 있습니다. 계속할까요?` → 진행 가능 | 실무에서 재작성·분할 계약이 있다. 막으면 사용자가 이름을 억지로 비튼다 |

**폼에서의 동작**: 4필드 위에 **표시명 미리보기**를 실시간으로 보여준다.
용역명이 비면 `2026 상반기 ____ 정기안전점검` 처럼 자리를 비워 표시한다 (미리보기 자체를 감추지 않는다).

**검색 매칭** (P1):
```
match(q, p) = squash(projectDisplayName(p)).includes(squash(q))
squash(s)   = s.toLowerCase().replace(/\s/g, '')
```
공백을 지우고 비교하므로 `2026상반기아파트` 로도 찾힌다. 검색 결과 0건이면 빈 상태 + `[검색어 지우기]`.

**목록 정렬**: `lastOpenedAt DESC`. 동률이면 `createdAt DESC`. (정렬 옵션 UI 는 두지 않는다.)

**최근 접속 상대시간** (`packages/project-core/src/relativeTime.ts`, 순수 함수 — `Date.now()` 를 인자로 받는다):

| 경과 | 표기 |
|---|---|
| < 60초 | `방금` |
| < 60분 | `n분 전` |
| < 24시간 | `n시간 전` |
| < 7일 | `n일 전` |
| 그 외 | `YYYY-MM-DD` |

`<time>` 요소의 `title`/`dateTime` 에 절대시각을 넣는다. 숫자는 `.num` (모노스페이스, 디자인시스템 §5).

### 2-6. 동(棟) 구성

| 조작 | 동작 |
|---|---|
| 추가 | 목록 끝에 인라인 입력 행이 열린다. 기본값 `동 {n}` 을 **선택 상태로** 넣어 바로 덮어쓸 수 있게 한다. `Enter` 확정 / `Esc` 취소 |
| 이름 변경 | 행 더블클릭 또는 `⋯ > 이름 변경` → 인라인 편집 |
| 순서 변경 | 드래그 핸들(`⠿`). 드롭 시 그 동의 `sortOrder` 를 `0,10,20…` 로 조밀 재부여 |
| 삭제 | `⋯ > 삭제`. 하위가 있으면 **확인 다이얼로그**: `'본관'을 삭제하면 층 4개 · 도면 3장 · 결함 27건이 함께 삭제됩니다.` 숫자를 반드시 실측해 넣는다 |
| 선택 | 동 1개 선택 → 우측 층 패널이 그 동의 층만 보여준다 |

- 이름 규칙: 1~40자, 같은 용역 안에서 **중복 허용**(경고 없음). 층과 달리 동 이름은 정렬에 쓰이지 않는다.
- 동이 0개일 때 층 패널은 빈 상태 `왼쪽에서 동을 먼저 추가해 주세요`.
- **동 1개만 있는 건물이 대다수다.** 용역 생성 직후 `본관` 동 1개를 자동 생성한다 —
  사용자가 지우거나 이름을 바꿀 수 있고, "동부터 만들어야 한다"는 빈 화면 장벽을 없앤다.

### 2-7. 층 sortOrder 규칙 (함정 #7)

> **불변식: `sortOrder` 는 정수이고, 오름차순 = 아래층 → 위층이며, 지하로 파싱된 층은 자동 부여 직후 반드시 음수다.**

#### 2-7-a. 이름 파싱 → 자동 부여 (`STEP = 10`)

| 입력 이름 (공백·대소문자 무시) | 해석 | sortOrder |
|---|---|---|
| `지하3층` `지하 3층` `B3` `b3` `B3F` | 지하 n | **`-n × 10`** → `-30` |
| `지상1층` `1층` `1F` `F1` | 지상 n | **`n × 10`** → `10` |
| `옥탑` `옥탑층` `PH` `R` `RF` | 옥탑 | **`9000`** |
| `옥상` `지붕층` | 옥상 | **`8000`** |
| `PIT` `피트` `기계실피트` | 최하단 | **`-9000`** |
| 그 외 전부 (`중2층` `A구역` `주차램프` …) | **파싱 실패** | **`max(그 동의 sortOrder) + 10`** (목록 맨 끝) |

**`STEP = 10` 인 이유**: 층 사이에 새 층을 끼울 자리를 남긴다.
중간층·중이층처럼 실무 표기가 갈리는 이름은 **파싱하지 않는다** — 잘못 해석하면 출력 순서가 조용히 틀린다.
대신 목록 끝에 넣고 **사용자가 드래그로 제자리에 놓게 한다.** 드래그가 최종 권한이다.

> **상세기획 §3-2 는 `지하4층=−4 … 지상1층=1 … 옥탑=99` 로 예시했다.**
> 이 문서는 **부호 규약(지하=음수)을 그대로 지키고 크기만 10배 격자로 확장**했다.
> 정수 `1`과 `2` 사이에는 층을 끼울 수 없기 때문이다. → §4 지적사항.

#### 2-7-b. 드래그 재배치

```
reorder(floors, movedId, newIndex):
  arr  = 배열에서 movedId 를 newIndex 로 옮긴 결과 (표시 순서 = 진실)
  prev = arr[newIndex-1]?.sortOrder ?? (arr[newIndex+1].sortOrder - 2*STEP)
  next = arr[newIndex+1]?.sortOrder ?? (prev + 2*STEP)
  if (next - prev >= 2):
      moved.sortOrder = floor((prev + next) / 2)      # 이웃 사이 중간 정수
  else:
      renumber(arr)                                    # 여유 없음 → 그 동 전체 재번호
```

```
renumber(arr):   # 표시 순서를 보존하면서 부호 규약을 복원한다
  belowCount = arr 중 '지하로 파싱되는 이름' 의 개수를 앞에서부터 센 값
               (연속 구간만. 중간에 지상이 끼면 거기서 멈춘다)
  앞 belowCount 개  → -(belowCount - i) * STEP     # …, -20, -10
  나머지 j 번째    →  (j + 1) * STEP               #  10,  20, …
```

- 사용자가 순서를 부호 규약과 모순되게 놓으면(지하3층을 지상2층 위로 끌었다) **사용자 순서가 이긴다.**
  경고하지 않는다 — 실무에는 우리가 모르는 층 표기가 있다.
- **`sortOrder` 숫자를 UI 에 노출하지 않는다.** 사용자는 드래그만 한다. 내부 값이다.
- 층 이름을 바꿔도 `sortOrder` 는 **자동으로 바뀌지 않는다.** 이미 정렬해 둔 순서를 이름 수정이 흐트러뜨리면 안 된다.
  대신 이름 변경 후 파싱 결과와 현재 위치가 어긋나면 행에 `순서 확인` 라벨을 조용히 띄운다.

#### 2-7-c. 전역 정렬 기준

```
층 정렬(출력·좌측 트리·층 전환)  =  (building.sortOrder, floor.sortOrder) 오름차순
```
`지하→지상` / `지상→지하` 출력 방향은 **상세기획 §4-4 의 층 칩 선택 순서** 문제이고 Phase 4 소관이다.
S1 은 관여하지 않는다.

### 2-8. 도면 업로드 흐름과 파일 처리

#### 2-8-a. 흐름

```
[층 행의 '도면 올리기'] 또는 [상단 도면 올리기]
   ↓  <input type=file multiple accept="image/*"> 또는 드롭존
1. 검증        MIME · 확장자 · 크기
2. 디코드      createImageBitmap({ imageOrientation: 'from-image' })
3. 래스터화    장변 상한 4096px, 확대는 최대 2배  (Phase 3 C8 규칙 재사용)
4. 썸네일      장변 320px
   ↓  PageCandidate[]  (이미지 1파일 = 1개 / PDF 1파일 = N개 — 후속)
5. 후보 목록   [썸네일] 파일명 · 2400×1600 · 1.8MB
               층 [지하3층 ▾]    도면 이름 [지하3층 결함조사 위치도]
6. [등록]      IndexedDB 트랜잭션 1회로 Drawing + Blob 3종을 함께 커밋
```

#### 2-8-b. 파일 처리 규칙

| 항목 | 값 · 동작 |
|---|---|
| 허용 MIME | `image/png` `image/jpeg` `image/webp` `image/svg+xml` |
| **PDF** | `application/pdf` 를 **명시적으로 인식**하고 거절한다: `PDF는 아직 지원하지 않습니다. PNG 또는 JPG로 변환해 올려주세요.` (조용히 무시하지 않는다 → Q13) |
| 그 외 형식 | 후보 목록에 **행으로 남기고** `지원하지 않는 형식` 배지. 나머지 파일은 정상 진행 |
| 파일당 상한 | **40MB** 초과 시 그 파일만 거절 |
| 1회 업로드 | **20장** 초과 시 앞 20장만 받고 경고 |
| 래스터화 | 장변 4096px 상한 · 확대 최대 2배 · 결과는 **PNG Blob** |
| SVG | `viewBox` / `width`·`height` 에서 원본 치수를 얻어 위 규칙으로 래스터화 |
| JPEG 회전 | EXIF orientation 을 **래스터화 시 적용**한다. 적용하지 않으면 도면이 90도 누워 뜬다 |
| 디코드 실패 | 그 행만 `이미지를 읽을 수 없습니다` 로 남기고 나머지 진행. **모달을 닫지 않는다** |
| 진행 표시 | 파일 3장 이상이면 `3장 중 2장 처리 중` |
| 층 자동 배정 | 파일명을 §2-7-a 파서에 넣어 같은 이름의 층이 있으면 자동 선택. 없으면 `층 선택` (미선택) |
| 도면 이름 기본값 | `${floor.name} 결함조사 위치도` (§G2 의 출력 텍스트). **사용자가 손대기 전까지는** 층을 바꾸면 따라 바뀐다. 한 번 편집하면 고정 |
| 등록 조건 | 층이 배정되지 않은 후보가 있으면 `[등록]` 비활성 + `층을 배정해 주세요` |

#### 2-8-c. 메모리 · Blob URL 수명

- 캔버스는 `URL.createObjectURL(renderBlob)` 로 도면을 읽는다.
- **URL 은 도면 단위로 캐시하고, 용역을 벗어날 때(P5 → P1/P3) 전부 `revokeObjectURL` 한다.**
  해제하지 않으면 층을 오갈 때마다 수 MB 씩 누수된다.
- 기존 `apps/web/src/canvas/imageLoader.ts` 의 캐시를 그대로 쓰되 **키를 `drawingId` 로 유지**하고
  `revokeAll(projectId)` 를 추가한다.

#### 2-8-d. 도면 교체 — 결함 좌표는 유지된다 ⚠️ (함정 #2)

이미 도면이 있는 층에 새 도면을 배정하면 **교체**다.

- 확인 다이얼로그: `'지하3층'의 도면을 교체합니다. 결함 27건의 표기 위치는 그대로 유지됩니다. (도면 해상도가 달라도 위치는 어긋나지 않습니다.)`
- **`Defect.drawingId` 를 새 도면 id 로 갱신**하고, `Mark.geometry`·`Label` 좌표는 **손대지 않는다.**
  정규화 좌표(0~1)이므로 해상도가 바뀌어도 상대 위치가 유지된다. 이것이 정규화의 존재 이유다.
- 옛 `Drawing` 레코드와 Blob 은 **즉시 삭제**한다(용량 회수). 결함이 딸리지 않으므로 안전하다.
- 교체는 Undo 대상이 아니다. 확인 다이얼로그가 그 자리를 대신한다.

### 2-9. 저장 전략 — **D5 확정: 브라우저 IndexedDB 영속 저장**

> **D5 원문 조건 4가지.** ① 새로고침해도 용역·도면·결함이 유지된다 ② Phase 5 로컬 DB 를 앞당기는
> 것이므로 **버리는 작업이 아니다** — Phase 5 가 그대로 이어받을 스키마여야 한다
> ③ **S1 은 로컬 영속 저장까지만.** 동기화·병합·큐를 만들지 않는다
> ④ **도면 이미지 원본을 Blob 으로 함께 보관**한다.

#### 2-9-a. 왜 IndexedDB 인가 (기각한 안)

| 안 | 판정 |
|---|---|
| 메모리만 | **탈락.** 새로고침하면 업로드한 도면이 사라진다. S1 의 존재 이유(테스트 가능성)와 정면 충돌 |
| `localStorage` | **탈락.** 5MB 상한. 도면 1장이 그것을 넘는다. 문자열 전용이라 Blob 을 base64 로 33% 부풀려야 한다 |
| **IndexedDB** | **채택 (D5).** Blob 원본 저장, 수백 MB, 인덱스, 트랜잭션. 불변식 3(오프라인 우선)이 어차피 요구하는 형태다 |
| File System Access API | **탈락.** Chrome 계열 전용 + 매번 권한 프롬프트 |

**새 npm 의존성을 추가하지 않는다.** `idb`·`dexie` 없이 원시 IndexedDB 를 약 150줄로 감싼다.
라이브러리를 고르는 순간 Phase 5 로컬DB 선택을 앞질러 굳히게 된다. 지금 필요한 것은 얇은 CRUD 뿐이다.

#### 2-9-b. 스키마 — **S2a~S5 가 얹힐 자리를 미리 비워 둔다** (D4)

D4 로 실행 순서가 `S1 → S2a → S3 → S4 → S2b → S5` 로 확정됐다.
**뒤 단계가 전부 이 스키마 위에 얹히므로, 스토어와 공통 필드를 지금 잡아 둔다.**
`S1 에서 데이터를 쓰는 스토어는 굵게` 표시했다. 나머지는 **빈 스토어로 생성만** 한다 —
스토어 추가는 IndexedDB 버전 업그레이드를 부르고, 그때마다 사용자 데이터가 마이그레이션 대상이 된다.

```
DB: 'onspect'   version: 1
┌────────────────┬─────────┬───────────────────────────────────────┬─────────────┐
│ store          │ keyPath │ index                                 │ 사용 시점    │
├────────────────┼─────────┼───────────────────────────────────────┼─────────────┤
│ **projects**   │ id      │ by_lastOpenedAt                       │ **S1**      │
│ **buildings**  │ id      │ by_project (projectId, sortOrder)     │ **S1**      │
│ **floors**     │ id      │ by_project, by_building               │ **S1**      │
│ **drawings**   │ id      │ by_project, by_floor                  │ **S1**      │
│ **defects**    │ id      │ by_project, by_drawing, by_floor      │ **S1**(캔버스)│
│ **blobs**      │ key     │ —  value: { blob, refCount, byteSize }│ **S1**      │
│ **meta**       │ key     │ —  schemaVersion · appVersion         │ **S1**      │
│ memos          │ id      │ by_project, by_drawing                │ S2a         │
│ itemSettings   │ id      │ by_project                            │ S3 · S4     │
│ photos         │ id      │ by_project, by_defect                 │ S5          │
└────────────────┴─────────┴───────────────────────────────────────┴─────────────┘
```

- `defects` 는 S1 에서 **캔버스가 이미 쓴다**(Phase 3 결과물이 붙으므로). 다만 S1 이 만드는
  결함 필드는 Phase 3 이 정의한 것까지이고, S4 의 결함정보 필드는 **레코드에 필드를 더할 뿐**
  스토어·인덱스를 바꾸지 않는다.
- `sketch`(자유그리기)는 `Defect` 안의 배열이므로 별도 스토어가 필요 없다.
- `ExportRun`(출력 이력 · 번호 스냅샷, 상세기획 §4-3)은 Phase 4 스토어다. **지금 만들지 않는다** —
  출력 파라미터 형태가 확정되지 않아 인덱스를 잘못 잡을 위험이 크고, 그때는 이미 스키마 버전을
  올릴 다른 이유들이 함께 온다.

#### 2-9-c. 모든 레코드가 갖는 공통 필드 — Phase 5 인계용

상세기획 §3-3 이 `createdBy, deviceId, createdAt, updatedAt` 을 **병합·감사용**으로 이미 요구한다.
**나중에 붙이면 기존 레코드 전부가 `null` 이라 병합이 그 구간을 판정할 수 없다.** 지금 넣는다.

```ts
type RecordBase = {
  createdAt: number;          // epoch ms
  updatedAt: number;          // 모든 쓰기에서 갱신. Phase 5 LWW 병합의 기준
  deviceId: string;           // 기기 식별자. 첫 실행 시 생성해 meta 에 보관
  createdBy: string | null;   // 사용자 개념은 Phase 5. S1 은 null
};
```

- `deviceId` 는 첫 실행 때 `crypto.randomUUID()` 로 만들어 `meta` 에 저장하고 이후 재사용한다.
- **S1 은 이 필드들을 채우기만 하고 읽지 않는다.** 병합 로직은 Phase 5 다 (D5 ③).
- 소프트 삭제 필드(`deletedAt`)는 `projects` 에만 둔다. 동·층·도면은 하드 삭제이고(§2-11),
  Phase 5 에서 tombstone 이 필요해지면 그때 필드를 더한다 — 삭제 의미가 화면마다 다르므로
  지금 전부에 붙이면 쓰이지 않는 상태값이 굳는다.

#### 2-9-d. 도면 Blob 보관 (D5 ④)

**새로고침 후 도면이 렌더되지 않으면 S1 은 실패한 것이다.** 그래서 Blob 보관을 규칙으로 못박는다.

| 규칙 | 내용 |
|---|---|
| 저장 대상 | 도면 1장당 **원본 Blob · 렌더 래스터 Blob · 썸네일 Blob** (§2-4 `Drawing`) |
| 저장 시점 | `[등록]` 을 누른 그 트랜잭션 안에서 `Drawing` 레코드와 **함께** 커밋한다. 레코드만 남고 Blob 이 없는 상태가 단 한 순간도 존재하면 안 된다 |
| 원자성 | 하나의 `readwrite` 트랜잭션에 `drawings` + `blobs` 를 함께 연다. 중간 실패 시 IndexedDB 가 통째로 롤백한다 |
| 로드 | 캔버스 진입 시 `renderBlobKey` → Blob → `createObjectURL`. **네트워크를 타지 않는다** |
| 참조 계수 | `blobs` 값은 `{ blob, refCount, byteSize }`. 구조 복사(§2-13)로 두 용역이 같은 Blob 을 가리킬 수 있으므로, `refCount === 0` 일 때만 실제 삭제 |
| 용량 표시 | P1 각 행에 `도면 9장 · 약 48MB`. §G3 오프라인 준비의 용량 고지와 같은 계산이므로 Phase 5 가 그대로 쓴다 |
| 저장 여유 확인 | 업로드 전 `navigator.storage.estimate()` 로 남은 용량을 확인하고, 부족하면 **업로드 전에** 거절한다. 처리 다 하고 마지막에 실패하는 것이 최악이다 |
| 영속성 요청 | 첫 도면 업로드 시 `navigator.storage.persist()` 를 1회 호출한다. 브라우저가 용량 압박 때 데이터를 자동 축출하는 것을 막는다. 거절되어도 앱은 그대로 동작한다 |

#### 2-9-e. 쓰기 규칙과 Phase 5 인계

| 규칙 | 내용 |
|---|---|
| **로컬 우선** | 모든 쓰기는 곧바로 메모리 상태에 반영되고, 저장은 그 뒤에 따라간다. **UI 가 저장 완료를 기다리지 않는다** (불변식 3). D5 가 이 원칙을 앞당겨 실현한다 |
| **커밋 시점에만 저장** | 드래그 중 매 프레임 저장하지 않는다. `applyCommand()` 가 커맨드를 확정할 때 1회 |
| 디바운스 | 250ms. 단 `visibilitychange`(hidden) · `beforeunload` · 라우트 이탈 시 **즉시 플러시** |
| 저장 단위 | **레코드 단위 upsert.** 결함 500건을 매번 통째로 직렬화하지 않는다 |
| 실패 처리 | quota 초과·차단(사생활 보호 모드) → 상단에 **지속 배너** `변경 사항을 저장하지 못했습니다`. 토스트로 흘려보내지 않는다. 앱은 메모리 상태로 계속 동작한다 |
| 초기화 | 설정 메뉴에 `[로컬 데이터 초기화]` (2단 확인) |
| **스키마 마이그레이션** | `meta.schemaVersion` 이 코드 버전보다 낮으면 **버전별 마이그레이션 함수를 순서대로 적용**한다(`migrations[]`). 자동 삭제하지 않는다. 마이그레이션이 없는 구간이면 안내 화면 `저장 형식이 바뀌었습니다` + `[초기화하고 계속]` / `[아무것도 하지 않기]` |
| **S1 이 만들지 않는 것 (D5 ③)** | 서버 클라이언트 · 동기화 큐 · 충돌 병합 · `syncState` 필드. **하나도 만들지 않는다.** 큐를 지금 만들면 서버 계약 없이 형식만 굳는다 |

**Phase 5 가 이어받는 것** — 이 문서는 다음을 Phase 5 의 발판으로 남긴다.

1. `RecordBase` 의 `updatedAt` · `deviceId` (§2-9-c) — 병합 판정의 재료
2. 레코드 단위 upsert 경로 — 동기화가 붙을 지점이 이미 한 곳으로 모여 있다
3. `ProjectRepo` 인터페이스 (§2-12) — 구현을 SQLite/서버 캐시로 갈아끼울 이음매
4. Blob refCount 와 용량 집계 — §G3 오프라인 준비·해제가 그대로 쓴다

#### 2-9-f. 사용자에게 고지할 것

P1 하단에 상시 1줄:
> `데이터는 이 브라우저에만 저장됩니다. 브라우저 데이터를 지우면 함께 사라집니다.`

**백업 수단은 S1 범위 밖이다.** 용역 내보내기/가져오기는 Phase 5 에서 다룬다.
저장이 로컬 단일본이라는 사실을 위 한 줄로 계속 노출하는 것이 S1 이 할 수 있는 전부다.

### 2-10. 선택 대상 가시성 규칙 (알려진 버그의 근본 원인)

> **빠져 있던 규칙: "선택한 대상은 항상 화면 안에 있어야 한다."**

버그 재현(1120px, 우측 결함정보 패널 열림)에서 선택된 번호 풍선이 가려진다.
정확한 가림 주체(그리드 컬럼이냐 떠 있는 툴 팔레트냐)는 **중요하지 않다.**
어느 쪽이든 원인은 하나다 — **캔버스가 "쓸 수 있는 영역"이 아니라 "요소 전체 크기"를 기준으로 뷰포트를 잡는다.**

#### 2-10-a. 안전 영역(safe rect) 개념 도입

```ts
// packages/canvas-core/src/visibility.ts   ← 신규 파일 (canvas-core 의 유일한 신규 모듈)
export type SafeInsets = { top: number; right: number; bottom: number; left: number };

/** 이미 안전 영역 안이면 null. 아니면 옮겨야 할 뷰포트를 돌려준다 */
export function ensureVisible(
  state: CanvasState, defects: readonly Defect[],
  globalStyle: GlobalStyle, defectId: string,
): Viewport | null;
```

- `CanvasState` 에 `safeInsets: SafeInsets` 를 추가한다(기본 전부 0).
- 새 입력 이벤트 `{ k: 'SET_SAFE_INSETS'; insets: SafeInsets }`.
- 웹 어댑터가 **떠 있는 UI 를 실측**해 넣는다: 우측 툴 팔레트 폭 + 여백, 하단 도움말 줄 높이,
  상단 여백. 레이아웃 컬럼(좌측 패널·우측 패널)은 캔버스 요소 밖이라 `ResizeObserver` 가 이미 처리한다.
  **둘 다 같은 안전 영역 계산에 흡수된다.**

#### 2-10-b. 판정과 보정

```
targetRect = 선택 결함의 마크 전부 + 라벨(풍선 반지름 포함) 을 감싸는 스크린 bbox
             를 REVEAL_PAD_PX(24) 만큼 팽창한 사각형
safeRect   = { x: insets.left, y: insets.top,
               w: canvas.w - insets.left - insets.right,
               h: canvas.h - insets.top  - insets.bottom }

1. targetRect ⊆ safeRect                → null (아무것도 하지 않는다)
2. targetRect 가 safeRect 보다 크면      → zoom 을 safeRect 에 맞을 때까지 낮춘다.
                                           단 fitZoom × ZOOM_MIN_FACTOR 미만으로는 내리지 않는다.
                                           그 뒤 safeRect 중앙에 놓는다
3. 그 외                                 → **축마다 필요한 만큼만** tx/ty 를 민다 (최소 이동)
```

| 규칙 | 값 |
|---|---|
| 발동 시점 | `SELECT_DEFECT(reveal:true)` · `RESIZE` · `SET_SAFE_INSETS` · `SET_DRAWING` 직후 선택이 남아 있을 때 |
| **발동하지 않는 시점** | **`state.drag !== null`** (드래그 중 화면이 손을 따라다니면 조작 불가) · 커맨드로 대상이 방금 이동한 직후 (사용자가 스스로 옮긴 결과다) |
| 팬 클램프와의 관계 | **이 규칙이 `PAN_KEEP_VISIBLE` 클램프보다 우선한다.** 도면 밖으로 끌려나간 라벨(§2-1-a)을 보여주려면 클램프를 넘어야 한다 |
| 애니메이션 | 없다. 즉시 이동 (기존 `REVEAL_DEFECT` 와 일관) |
| Undo | 대상 아님 (B9 유지) |
| 새 상수 | `REVEAL_PAD_PX = 24` → `constants.ts` |

#### 2-10-c. 함께 고치는 알려진 결함 2건

| 결함 | 원인 | 처리 |
|---|---|---|
| 도면 없는 층에서 줌 배율 표시가 빈칸 | `.zoom` 에 최소 폭이 없어 대체 문자가 눌린다 | `min-width: 4.5ch` + 항상 `—` 표시 + `title="도면이 없습니다"`. 배율 자리가 흔들리지 않게 고정 |
| `도면이 없습니다` 문구 중복 (`Sidebar.tsx:104`, `CanvasView.tsx:263`) | 같은 사실을 두 곳에서 말한다 | **캔버스에만 남긴다.** 좌측 층 행에는 작은 `도면 없음` 배지만 둔다. 캔버스 빈 상태에는 **행동 버튼** `[이 층에 도면 올리기]` 를 넣어 P4 로 보낸다 |

### 2-11. 확인 다이얼로그 · 삭제 정책

| 대상 | 정책 |
|---|---|
| **용역 삭제** | **소프트 삭제** (`deletedAt`). 목록에서 즉시 사라지고 토스트 `'{표시명}'을 삭제했습니다 [되돌리기]` (10초). 되돌리기를 놓치면 복구 UI 는 없다 — 레코드는 남아 있으므로 Phase 5 에서 복원 경로를 붙일 수 있다 |

### 2-13. 이전 회차 연결 — S1 에서 어디까지 하나

D2 는 `Project = 1회차`, `prevProjectId` 로 잇기를 확정했다. S1 의 선은 다음과 같이 긋는다.

| 항목 | S1 | 근거 |
|---|---|---|
| `Project.prevProjectId` 필드 | **포함** | 나중에 넣으면 기존 용역이 전부 `null` 로 굳는다. 필드는 지금 만든다 |
| P2 폼의 `이전 회차 연결 (선택)` 드롭다운 | **포함** | 같은 용역명을 가진 용역을 위로 올려 추천한다 |
| **동 · 층 · 도면 구조 복사** | **포함 (S1-T12, 후순위)** | 도면 재업로드 부담 제거가 A안 채택의 조건이었다(§2-1). Blob 은 **복사하지 않고 같은 키를 참조**한다 |
| **결함 승계 · `prevDefectId` · 상태 3종** | **제외** | `PREV_PENDING`/`CURRENT`/`REPAIRED` 전이와 번호 승계는 Phase 2-D 의 본체다. 여기서 반쪽으로 만들면 갈아엎는다 |

**버튼 문구를 정확히 쓴다**: `[이전 용역의 동·층·도면 복사]`.
"전차 등록"이라고 쓰면 결함까지 왔다고 오해한다. 복사 후 토스트: `동 2개 · 층 9개 · 도면 9장을 복사했습니다. 결함은 복사되지 않습니다.`

**Blob 공유의 대가**: 두 용역이 같은 `blobKey` 를 참조하므로 **도면 Blob 삭제는 참조 카운트를 확인**해야 한다.
`blobs` 스토어에 `refCount` 를 두고, 0 이 될 때만 실제로 지운다.

## 3. 기존 픽스처 → 실데이터 교체 계획

**원칙 두 가지.**
1. **회귀 기준점을 잃지 않는다.** 현재 픽스처 8건(극단 종횡비 도면·미완성 결함·전회차·보수완료 포함)은 Phase 3 스냅·히트·상태색을 검증하는 유일한 자산이다. **지우지 말고 이사시킨다.**
2. **모듈 경계를 깨지 않는다.** canvas-core 는 §2-4-a 의 한 줄과 §2-10-a 의 파일 하나 외에 건드리지 않는다.
