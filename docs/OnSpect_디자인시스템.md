## 1. 선택: 캔버스 UI(023) 뼈대 + 애널리틱스 라이트(105) 데이터 표현

| 출처 | 가져온 것 |
|---|---|
| **[023] 캔버스 UI** | 화면 구조 — 넓은 작업공간 + 플로팅 툴바 + 좌측 고정 패널. 밝은 회색 배경(`#eceff5`) |
| **[105] 애널리틱스 라이트** | 데이터 표현 — 얇은 경계선, 명확한 숫자, **radius 3px(각진 모서리)** |
| **[055] 블루프린트 테크** | 숫자용 모노스페이스 서체 **하나만** |

### 왜 캔버스 UI인가

우리 화면이 문자 그대로 그것이다. 도면이라는 큰 작업공간 위에 플로팅 툴바가 뜨고,
좌측에 동>층 트리와 결함 리스트가 고정된다. 젠트릭스 실제 화면 구조와도 일치한다.

밝은 회색 배경(`#eceff5`)이 결정적이다. **흰 도면이 회색 위에 놓이면 "종이"로 보인다.**
도면이 화면의 주인공이 되고 UI는 뒤로 물러난다.

### 왜 애널리틱스 라이트를 섞는가

이 앱은 **계측 도구**다. 폭 0.2mm, 길이 2000mm, 면적 0.0004㎡ 같은 숫자가 화면을 채운다.
`radius 22px` 의 둥근 카드는 계측 도구의 신뢰감을 깎는다. **radius 3px** 로 각지게 간다.

## 2. 블루프린트 테크(055)를 쓰지 않는 이유

아틀라스에서 이 스타일의 `field` 는 `엔지니어링 · CAD · 제조` 다. 도메인이 정확히 맞아서 가장 먼저 끌린다.
**그런데 우리한테는 틀렸다.**

> 우리 캔버스에는 **이미 진짜 도면**이 들어간다. 흑백 선화, 격자, 치수선, 통심선이 가득한.
> 여기에 청사진 격자 배경을 깔면 **진짜 도면과 가짜 격자가 경쟁한다.**

블루프린트는 "도면이 없는 화면을 도면처럼 보이게" 할 때 쓰는 스타일이다.
도면이 실제로 있으면 그 위에 얹을 이유가 없다.

> 참고: 이전 세션의 UI 목업 v1이 정확히 블루프린트 네이비로 갔고,
> 사용자가 실제 젠트릭스 스크린샷을 제시하며 다시 만들라고 했다. 같은 실수를 반복하지 않는다.

블루프린트에서 가져올 것은 **숫자용 모노스페이스 서체** 하나뿐이다.

## 3. 색 예약 — 아틀라스를 그대로 베끼면 안 되는 지점

**이 앱에는 색이 이미 예약되어 있다.** 도면 위 결함 색은 도메인 규칙이지 디자인 선택이 아니다.

| 예약색 | 의미 | 누가 정했나 |
|---|---|---|
| 🔴 빨강 | 현회차 결함 (`CURRENT`) | 도메인 관행 · 젠트릭스 실측 |
| 🟣 보라 | 전회차 결함 (`PREV_PENDING`) | 동일 |
| ⚪ 회색 | 보수완료 (`REPAIRED`) | 동일 |

캔버스 UI(023)의 기본 accent 는 **보라 `#7657e8`** 다. 그대로 쓰면
**UI 버튼과 도면 위 전회차 마커가 같은 색이 된다.** 현장에서 혼동이 난다.

→ **accent 를 파랑 `#2d6cdf`(애널리틱스 라이트) 로 교체한다.**
파랑은 결함 색으로 쓰이지 않으므로 UI 전용으로 안전하게 예약할 수 있다.

가이드선도 같은 문제를 겪는다. 업계 관행은 마젠타(Figma·PowerPoint)지만
우리는 보라가 이미 전회차다. → **시안 `#00b8d4`** 로 간다.
흑백 도면·적/보라 결함·파랑 UI 어느 쪽과도 겹치지 않는다.

## 4. 토큰

```css
:root{
  /* 표면 */
  --paper:      #ffffff;  /* 도면 종이 */
  --bg:         #eceff5;  /* 앱 배경 — 도면을 종이로 띄운다 */
  --surface:    #ffffff;  /* 패널 · 툴바 · 카드 */
  --surface-2:  #f5f7fa;  /* 중첩 표면 · 리스트 헤더 */

  /* 텍스트 */
  --text:       #1f2734;
  --text-muted: #666b73;
  --text-dim:   #9aa4b0;

  /* 선 */
  --border:     #d9dee8;
  --border-2:   #eef1f6;

  /* UI 전용 강조 — 도면 위에는 절대 쓰지 않는다 */
  --accent:      #2d6cdf;
  --accent-weak: #e8f0fd;
  --accent-ink:  #1b4ba8;

  /* 도면 위 예약색 — UI가 쓰지 않는다 */
  --defect-current:  #e5342a;
  --defect-prev:     #7c4dff;
  --defect-repaired: #9aa4b0;

  /* 캔버스 보조 */
  --guide:      #00b8d4;   /* 스마트 정렬 가이드선 · 각도 스냅 표시 */
  --selection:  #2d6cdf;   /* 선택 핸들 (UI 계열) */

  /* 상태 */
  --ok:    #2d8a66;
  --warn:  #e3a535;
  --error: #d0342c;

  /* 형태 — 각지게. 계측 도구다 */
  --radius:    3px;
  --radius-lg: 6px;
  --shadow:    0 2px 8px rgba(31,39,52,.08);
  --shadow-float: 0 6px 24px rgba(31,39,52,.16);  /* 플로팅 툴바 */

  /* 서체 */
  --font-ui:  Pretendard, "Noto Sans KR", -apple-system, "Segoe UI", sans-serif;
  --font-num: ui-monospace, SFMono-Regular, Menlo, Consolas, monospace;
}
```

### 다크 모드는 하지 않는다 (1차)

도면은 흰 종이다. 앱을 어둡게 해도 캔버스 한가운데는 계속 흰색이라
명암 대비가 오히려 눈을 피로하게 만든다. 현장은 대체로 밝은 곳이다.
필요해지면 **패널만** 어둡게 하는 방식을 검토한다.

## 5. 숫자는 모노스페이스로

```css
.num { font-family: var(--font-num); font-variant-numeric: tabular-nums; }
```

적용 대상: 결함번호 · 사진번호 · 폭 · 길이 · 면적 · 개소 · 층 표기

이유 두 가지.
1. 표에서 자릿수가 세로로 정렬된다 (손상결함표가 전부 숫자다)
2. **`0.2` 와 `0.02` 를 눈으로 구분할 수 있다.** 균열 폭에서 이건 10배 차이다

## 6. 밀도 — PC와 모바일을 분리한다

같은 토큰을 쓰면 한쪽이 반드시 망가진다.

| | PC (사무실) | 모바일 (현장) |
|---|---|---|
| 리스트 행 높이 | 32px | 48px |
| 버튼 최소 높이 | 30px | **44px** |
| 본문 | 13px | 15px |
| 패널 여백 | 12px | 16px |
| 마커 히트 반경 | 8px (마우스) | **20px** (손가락) |

현장에서는 장갑을 낀 손으로, 밝은 햇빛 아래에서, 서서 조작한다.
**터치 타겟 44px 는 타협 대상이 아니다.**

반대로 PC는 정보 밀도가 생명이다 — 결함 100건을 스크롤 없이 훑을 수 있어야 한다.

## 7. 캔버스 위 UI 규칙

도면을 가리는 순간 도구로서 실패한다.

| 규칙 | 이유 |
|---|---|
| 플로팅 툴바는 **불투명 + 그림자** | 반투명이면 도면 선과 겹쳐 글자가 안 읽힌다 |
| 툴바는 선택된 대상 **근처**에 뜨되 대상을 덮지 않는다 | 젠트릭스 방식 |
| 좌측 패널은 접을 수 있다 | 도면 전체를 볼 때 필요 |
| 도면 위 텍스트에는 얇은 흰 외곽선(halo) | 검은 도면선 위에서도 번호가 읽힌다 |
| 가이드선은 **1px 점선**, 시안 | 얇아야 도면을 방해하지 않는다 |
| 마커 색은 결함 상태가 정한다. 사용자 커스텀은 그 위에 덮어쓴다 | 상속 규칙 (상세기획 §3-5) |

## 8. 적용 우선순위

1. 색 예약(§3)과 캔버스 위 UI 규칙(§7) — **어기면 기능이 망가진다**
