# OnSpect 구현

확정된 스펙을 **실제로 동작하는 코드**로 만든다.

## 절대 어기지 않는 도메인 불변식 8종

이건 취향이 아니다. 틀리면 제품이 망가지거나 보고서 수치가 틀린다.

### 1. 도면 좌표는 0~1 정규화

```
저장:  { x: 0.4213, y: 0.7788 }      ✓
저장:  { x: 842, y: 1557 }            ✗ 도면 해상도 바뀌면 전부 어긋남
```
화면 렌더링 시점에만 뷰포트 크기를 곱한다. DB·동기화 페이로드에는 정규화 좌표만 오간다.

### 2. 출력 번호는 저장하지 않는다

`defectNo`, `photoNo` 컬럼을 만들면 안 된다. 출력 시점에 계산한다.
저장되는 것은 `seq`(층 내 입력순번) 하나뿐이다.

이유: 병합·층 재정렬·필터 변경 때마다 번호가 달라져야 하는데, 저장하면 동기화가 깨진다.

### 3. 모든 쓰기는 로컬 우선

```
사용자 입력 → 로컬 DB 쓰기 → UI 즉시 반영 → (나중에) 동기화 큐 → 서버
                                              ↑ 실패해도 데이터는 안전
```
서버 응답을 `await` 한 뒤 로컬에 쓰는 코드는 현장에서 앱을 멈추게 한다.
동기화 큐는 **앱 재시작 후에도 살아있어야** 한다 (메모리 아님, 영속 저장).

### 4. 면적 계산

```
면적(㎡) = trunc( (폭mm / 1000) * (길이mm / 1000), 소수4자리 )
```
- **절사**이지 반올림이 아니다 (`0.1 × 2500 = 0.00025 → 0.0002`)
- **개소(EA)는 곱하지 않는다.** 면적은 1개소 기준값
- `AREA` 모드면 폭·길이는 0이고 면적을 직접 받는다

### 5. 층 sortOrder 는 정수, 지하는 음수

```
지하4층 = -4 … 지하1층 = -1, 지상1층 = 1 … 옥탑 = 99
```
문자열 정렬(`"지하10층" < "지하2층"`)은 무너진다.

### 6. 항목 계층은 마스터 + 연결

```
CauseMaster(orgId, 이름, 코드번호)              ← 조직에 하나
Link_DefectType_Cause(defectTypeId, causeMasterId, isDefault, sortOrder)
```
`Cause` 테이블에 `defectTypeId` 를 직접 박으면 "건조수축" 을 결함유형마다 다시 등록하게 되고,
손상결함표의 발생원인 코드번호가 프로젝트마다 달라진다.

### 7. 과업 생성 시 항목설정 스냅샷

과업은 조직 설정을 **참조(FK)하지 않고 복사**한다.
2025년 용어로 만든 보고서가 2026년 설정 변경으로 바뀌면 안 된다.

### 8. 사진 isPrimary 는 정확히 1장

결함당 사진 N장, 그중 대표 1장. 저장·삭제·대표지정 모든 경로에서
`isPrimary` 가 0개나 2개가 되는 순간이 없어야 한다. 대표 사진 삭제 시 다음 사진이 승계한다.

## 번호 계산 — 순수 함수로 격리

이 제품의 심장이다. **한 곳에만 존재해야 한다.**

```
assignNumbers(defects, options) → { defectNo: Map, photoNo: Map }

options = {
  floorOrder,       // 사용자가 고른 순서 (배열). 정렬 방향 라디오가 아님
  numberingMode,    // 'RESET_PER_FLOOR' | 'CONTINUOUS'
  scopeFilter,      // 'ALL' | 'EXTERIOR_ONLY' | 'DETAILED_ONLY'
  includeRepaired,  // boolean
}
```

규칙:
1. 필터를 **먼저** 적용하고 번호를 매긴다
2. 층 순서는 `floorOrder` 배열 순서를 그대로 따른다
3. 사진번호 카운터는 **대표사진이 있는 결함에서만** 증가한다 ← 가장 자주 틀린다
4. 부수효과 없음. DB 접근·전역 상태 참조 없음
5. 결과는 `ExportRun` 에 스냅샷 저장 → 재다운로드 시 동일 번호 재현

이 로직을 UI·DB·출력 코드에 복제하지 않는다. 복제하는 순간 세 곳이 어긋나기 시작한다.

## 작업 규율

### 스펙에 없는 것은 만들지 않는다

"있으면 좋을 것 같아서" 추가하지 않는다. 범위를 늘리는 것은 사용자의 결정이다.
필요해 보이면 QUESTIONS.md 에 적고 묻는다.

반대로 **스펙에 있는 것은 전부 만든다.** 어려운 부분만 남기고 완료 보고하지 않는다.

### 오프라인을 나중에 붙이지 않는다

"일단 온라인으로 만들고 나중에 오프라인 대응" 은 이 제품에서 반드시 실패한다.
로컬 DB를 진실의 원천으로 두고 시작한다.

### 작게 완성하고 즉시 넘긴다

모듈 하나가 끝날 때마다 code-reviewer 에게 알린다.
전부 만든 뒤 한꺼번에 검증받으면 경계면 버그가 누적되어 수정 비용이 폭증한다.

### 브라우저를 띄우지 않는다

개발 서버 실행·화면 조작·스모크 확인을 하지 마라. **런타임 확인은 사용자가 한다.**

대신 코드로 확인할 수 있는 것을 전부 확인한다 — 타입 검사, 단위 테스트,
프로덕션 빌드, `ui-quality.md` §7-1 의 코드 점검 7가지.
타입 캐스팅·제네릭·`any` 로 빠져나갈 구멍을 만들지 않는 것이 그만큼 더 중요해진다.

클릭해봐야 아는 것은 **`## 직접 확인해주실 것` 체크리스트**로 넘긴다.
사용자가 오류를 알려주면 `onspect-fix` 로 그 오류만 고친다.

## 기술 스택

기획서 기준 **React Native (Expo)** 모바일 + **웹** PC 화면 + 동기화 서버.

> 스택 세부(로컬 DB 라이브러리, 캔버스 렌더링 방식, 서버 구성)는 상세기획 Phase 7 에서 확정된다.
> 확정 전이라면 **선택이 아키텍처를 바꾸는 결정**이므로 임의로 정하지 말고 질문한다.

선택 시 판단 기준:
- 오프라인 로컬 DB: 영속 큐 지원, 대용량 사진 경로 관리, 마이그레이션
- 도면 캔버스: 큰 이미지 위 수백 개 마커의 줌/팬 성능, 히트 테스트 정확도
- 사진: 원본 보존 + 비파괴 편집(crop/rotate/annotation 은 메타로 저장)
