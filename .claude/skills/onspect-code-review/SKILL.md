# OnSpect 코드 검수

**틀린 것만 지적한다.** 취향은 지적하지 않는다.

모든 지적은 `이 입력에서 이렇게 깨진다` 또는 `스펙 X와 다르다` 로 말할 수 있어야 한다.
그렇게 말할 수 없으면 지적하지 않는다.

## 검수 순위

| 순위 | 유형 | 예 |
|---|---|---|
| 1 | 도메인 불변식 위반 | 출력번호를 DB에 저장 |
| 2 | 스펙 불일치 | 사진 1장만 되게 만듦 (스펙은 N장) |
| 3 | 정확성 버그 | 사진 없는 결함에서 사진번호가 증가 |
| 4 | 중복·과설계 | 번호 계산이 세 곳에 복제 |

**지적하지 않는 것**: 변수명 선호, 주석 분량, 파일 배치 취향, 포매팅.

## 불변식 8종 — 코드에서 직접 확인

"지켰겠지" 로 넘기지 않는다. 각 항목마다 실제 코드를 열어 확인하고 근거를 남긴다.

| # | 불변식 | 확인 방법 |
|---|---|---|
| 1 | 좌표 0~1 정규화 | 마커 저장/로드 경로에 픽셀값이 들어가는 곳이 없는지 |
| 2 | 출력번호 미저장 | 스키마·타입에 `defectNo`/`photoNo` 컬럼이 있으면 **즉시 심각** |
| 3 | 로컬 우선 쓰기 | 서버 응답을 `await` 한 뒤 로컬에 쓰는 경로가 있는지. 동기화 큐가 영속인지 |
| 4 | 면적 계산 | 나눗셈 순서, **절사**(반올림 아님), 개소를 곱하지 않는지 |
| 5 | 층 정렬 | 문자열 비교가 아니라 `sortOrder` 정수 비교인지 |
| 6 | 마스터+연결 | 원인·보수방안 테이블에 `defectTypeId` 외래키가 직접 박혔는지 |
| 7 | 설정 스냅샷 | 과업 생성이 설정을 복사하는지, FK 참조만 하는지 |
| 8 | isPrimary 1장 | 저장·삭제·대표지정 경로에서 0개/2개가 되는 순간이 있는지 |

## 정밀 검수 — 번호 계산 함수

이 제품의 심장이다. 전 항목을 확인한다.

- [ ] 순수 함수인가 (DB 접근·전역 상태 참조 없음)
- [ ] 같은 입력 → 항상 같은 출력인가
- [ ] 층 순서가 **사용자가 고른 배열 순서**를 따르는가 (정렬 방향 라디오가 아님)
- [ ] `층별 리셋` / `전체 연속` 두 모드 모두 정확한가
- [ ] **사진 없는 결함에서 사진번호 카운터가 증가하지 않는가** ← 최빈 버그
- [ ] 필터가 번호 부여 **전에** 적용되는가
- [ ] `ExportRun` 스냅샷으로 재다운로드 시 재현되는가
- [ ] 이 로직이 다른 곳에 복제되어 있지 않은가

## 정밀 검수 — 오프라인 동기화

- [ ] 로컬 쓰기 성공 즉시 UI 반영 (서버 대기 없음)
- [ ] 네트워크 실패가 데이터 손실로 이어지지 않는가
- [ ] 동기화 큐가 앱 재시작 후에도 살아있는가 (메모리 아님)
- [ ] 재시도가 중복 업로드를 만들지 않는가 (멱등성)
- [ ] 병합 시 `deviceId` / `updatedAt` 로 출처 구분 가능한가
- [ ] 사진 파일이 로컬 경로 → 서버 URL 전환 중 유실되지 않는가

## 심각도

| 등급 | 기준 | 처리 |
|---|---|---|
| **심각** | 불변식 위반, 데이터 손실, 보고서 수치 오류 | 반드시 수정. 반려 사유 |
| **보통** | 특정 조건에서 오동작 | 수정하는 것이 옳다 |
| **경미** | 중복·복잡도 | 여유 있을 때 |

## 지적 작성 형식

지적은 **고칠 수 있게** 써야 한다. 파일:라인 + 재현 + 수정 방법이 없으면 지적이 아니라 감상이다.

```markdown
### [심각] 사진 없는 결함에서 사진번호가 증가한다
- 파일: `src/export/assignNumbers.ts:57`
- 문제: 카운터를 결함 루프 시작 시 무조건 증가시킨다
- 재현: 결함 3건 중 2번째에 사진이 없으면 → 사진번호 1, 3 (2가 비어버림)
- 기대: 사진번호 1, 2
- 수정: `if (defect.photos.some(p => p.isPrimary))` 안에서만 증가
```

## 판정

| 판정 | 기준 |
|---|---|
| **통과** | 심각 0건 |
| **조건부 통과** | 심각 0건, 보통 있음 — 진행하되 수정 예정 |
| **반려** | 심각 1건 이상 |

## 확인하지 못한 것을 숨기지 않는다

읽지 못한 영역, 판단할 수 없었던 부분은 `## 확인하지 못한 것` 에 명시한다.
검수했다고 적었는데 안 본 코드가 있으면, 그게 가장 위험하다.

## 재검수 시

이전 지적이 **실제로 고쳐졌는지 코드에서 직접** 확인한다.
builder 의 "고쳤습니다" 를 근거로 `해결됨` 을 적지 않는다.
각 항목에 `해결됨 / 미해결 / 부분해결` 을 표시하고, 새로 발견한 것만 추가한다.
