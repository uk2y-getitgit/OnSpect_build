# OnSpect 오류 수정

**사용자가 직접 써보다가 발견한 오류**를 고친다.

이 스킬의 전제는 하나다: **실행해서 확인하는 일은 사용자가 이미 했다.**
따라서 재현하겠다고 브라우저를 띄우지 않는다. 코드에서 원인을 찾는다.

## 왜 이 방식인가

> 사용자 지시 (2026-08-22):
> *"직접 구현된 기능을 웹에서 실행하고 검증하는 과정이 너무 오래걸리고 예산을 너무 많이 사용되고 있어.
>  UI와 직접 작업을 진행하는 건 내가 하고, 오류를 다시 알려주면
>  해당 오류에 대한 확인과 수정만 다시 진행해줘."*

에이전트가 브라우저를 조작하며 버그를 찾는 것은 **느리고 비싸다.**
사람이 5초에 발견하는 것을 에이전트는 수십 번의 도구 호출로 찾는다.
그래서 **발견은 사람이, 수정은 에이전트가** 한다.

## 절차

### 1. 신고 내용을 정확히 읽는다

사용자가 준 것: 무엇을 했고, 무엇이 보였고, 무엇을 기대했는가.
셋 중 빠진 것이 있으면 **추측하지 말고 묻는다.** 특히 "어디서" 가 빠지면 못 고친다.

되묻기 전에 스스로 답할 수 있는지 먼저 본다 — 화면 이름·조작 이름이 코드에서 유일하게 특정되면 묻지 않는다.

### 2. 코드에서 원인을 찾는다

**Serena 심볼 도구를 쓴다. 파일 전체를 읽지 마라.**

```
search_for_pattern      증상과 관련된 문자열·핸들러 후보 찾기
get_symbols_overview    그 파일의 심볼만 훑기
find_symbol             필요한 본문만 (include_body=True)
find_referencing_symbols 이 함수를 누가 부르는가 = 영향 범위
```

증상 → 후보 지점 매핑:

| 증상 | 먼저 볼 곳 |
|---|---|
| 안 눌린다 / 반응 없다 | 이벤트 핸들러 바인딩, `disabled` 조건, 히트 테스트 우선순위 |
| 화면이 깨진다 / 겹친다 | `styles.css` 해당 클래스, 그리드·flex 정의, 브레이크포인트 |
| 값이 틀리다 | 계산 함수 (면적·번호·좌표 변환). **단위 변환과 정규화↔스크린을 먼저 의심** |
| 저장이 안 된다 | IndexedDB repo, 저장 큐, 커밋 시점 |
| 새로고침하면 사라진다 | Blob 보관, 스토어 누락 |
| 선택이 안 된다 / 엉뚱한 게 잡힌다 | 히트 테스트 우선순위 |
| 되돌리기가 안 먹는다 | 커맨드 패턴 편입 누락 |

### 3. 고친다 — 좁게

**신고된 오류 하나만 고친다.**

- 주변 코드를 정리하지 않는다
- "이왕 보는 김에" 리팩터하지 않는다
- 눈에 띈 다른 문제는 **고치지 말고 보고에 적는다.** 고칠지는 사용자가 정한다

범위를 넓히면 새 버그가 생기고, 사용자가 방금 확인한 정상 동작이 깨진다.

### 4. 검증한다 — 코드로

```
타입 검사  →  단위 테스트  →  프로덕션 빌드
```

**브라우저를 띄우지 않는다.** 실행 확인은 사용자가 한다.

고친 것이 계산 로직이면 **그 케이스를 단위 테스트로 고정하라.**
같은 버그가 두 번 나오지 않게 하는 유일한 방법이다.

### 5. 보고한다

```markdown
## 무엇이 문제였나
{한 문장. 증상이 아니라 원인}

## 어디를 고쳤나
`path/to/file.ts:functionName` — {무엇을 어떻게}

## 왜 그렇게 됐나
{근본 원인. 같은 실수가 다른 데도 있는지}

## 검증
타입 ✅ / 테스트 N개 ✅ / 빌드 ✅
(회귀 테스트를 추가했으면 명시)

## 다시 확인해주세요
{사용자가 눌러볼 정확한 절차}

## 고치지 않은 것
{눈에 띄었지만 범위 밖이라 남겨둔 것}
```

## 원인을 못 찾았을 때

**추측으로 고치지 마라.** 증상만 가리는 수정은 원인을 숨겨서 나중에 더 비싸진다.

대신 보고한다:
- 어디까지 확인했는가
- 무엇을 배제했는가
- 사용자에게 필요한 추가 정보 (콘솔 에러 메시지, 창 크기, 어느 도면, 어떤 순서)

**콘솔 에러 메시지 한 줄이 있으면 대부분 즉시 특정된다.** 없으면 요청하라.

## 여러 건이 한꺼번에 왔을 때

1. **먼저 분류한다** — 같은 원인인가, 별개인가
2. 같은 원인이면 하나로 묶어 한 번에 고친다
3. 별개면 **심각한 것부터** 순서대로. 데이터가 틀리는 것 > 안 되는 것 > 보기 싫은 것
4. 하나 고칠 때마다 타입·테스트를 돌린다. 몰아서 돌리면 어느 수정이 깼는지 모른다
