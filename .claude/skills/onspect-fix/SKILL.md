# OnSpect 오류 수정

**사용자가 직접 써보다가 발견한 오류**를 고친다.

이 스킬의 전제는 하나다: **실행해서 확인하는 일은 사용자가 이미 했다.**
따라서 재현하겠다고 브라우저를 띄우지 않는다. 코드에서 원인을 찾는다.

## 왜 이 방식인가

> 사용자 지시 (2026-08-22):
> *"직접 구현된 기능을 웹에서 실행하고 검증하는 과정이 너무 오래걸리고 예산을 너무 많이 사용되고 있어.
>  UI와 직접 작업을 진행하는 건 내가 하고, 오류를 다시 알려주면
>  해당 오류에 대한 확인과 수정만 다시 진행해줘."*

에이전트가 브라우저를 조작하며 버그를 찾는 것은 **느리고 비싸다.**
사람이 5초에 발견하는 것을 에이전트는 수십 번의 도구 호출로 찾는다.
그래서 **발견은 사람이, 수정은 에이전트가** 한다.

## 절차

### 1. 신고 내용을 정확히 읽는다

사용자가 준 것: 무엇을 했고, 무엇이 보였고, 무엇을 기대했는가.
셋 중 빠진 것이 있으면 **추측하지 말고 묻는다.** 특히 "어디서" 가 빠지면 못 고친다.

되묻기 전에 스스로 답할 수 있는지 먼저 본다 — 화면 이름·조작 이름이 코드에서 유일하게 특정되면 묻지 않는다.

### 2. 코드에서 원인을 찾는다

**Serena 심볼 도구를 쓴다. 파일 전체를 읽지 마라.**

```
search_for_pattern      증상과 관련된 문자열·핸들러 후보 찾기
get_symbols_overview    그 파일의 심볼만 훑기
find_symbol             필요한 본문만 (include_body=True)
find_referencing_symbols 이 함수를 누가 부르는가 = 영향 범위
```

증상 → 후보 지점 매핑:

| 증상 | 먼저 볼 곳 |
|---|---|
| 안 눌린다 / 반응 없다 | 이벤트 핸들러 바인딩, `disabled` 조건, 히트 테스트 우선순위 |
| 화면이 깨진다 / 겹친다 | `styles.css` 해당 클래스, 그리드·flex 정의, 브레이크포인트 |
| 값이 틀리다 | 계산 함수 (면적·번호·좌표 변환). **단위 변환과 정규화↔스크린을 먼저 의심** |
| 저장이 안 된다 | IndexedDB repo, 저장 큐, 커밋 시점 |
| 새로고침하면 사라진다 | Blob 보관, 스토어 누락 |
| 선택이 안 된다 / 엉뚱한 게 잡힌다 | 히트 테스트 우선순위 |
| 되돌리기가 안 먹는다 | 커맨드 패턴 편입 누락 |

**"왜 여기서 X를 안 하는지"를 설명하는 주석은 그대로 믿지 마라.** 그 주석이 막고 있던
문제가 이후 다른 커밋에서 이미 해결됐을 수 있다 — 주석은 안 지워지고 조용히 낡는다.
그 주석이 결정적 근거일 때는 `git log -S"<주석이 정당화하는 코드/선택자>"`로 도입 시점을
찾고, 주석이 탓하는 대상(컴포넌트·라이브러리 호출·API)이 그 뒤에 바뀌었는지 확인한 다음
판단한다. 한두 번의 도구 호출이면 되고, "코드가 의도적으로 이렇게 돼 있다"고 잘못 결론
내리거나 이미 사라진 제약을 피하려 필요 이상으로 복잡한 우회를 만드는 것보다 싸다.

### 3. 고친다 — 좁게

**신고된 오류 하나만 고친다.**

- 주변 코드를 정리하지 않는다
- "이왕 보는 김에" 리팩터하지 않는다
- 눈에 띈 다른 문제는 **고치지 말고 보고에 적는다.** 고칠지는 사용자가 정한다

범위를 넓히면 새 버그가 생기고, 사용자가 방금 확인한 정상 동작이 깨진다.

### 4. 검증한다 — 코드로

```
타입 검사  →  단위 테스트  →  프로덕션 빌드
```

**브라우저를 띄우지 않는다.** 실행 확인은 사용자가 한다.

고친 것이 계산 로직이면 **그 케이스를 단위 테스트로 고정하라.**
같은 버그가 두 번 나오지 않게 하는 유일한 방법이다.

### 5. 보고한다

```markdown
## 무엇이 문제였나
{한 문장. 증상이 아니라 원인}

## 어디를 고쳤나
`path/to/file.ts:functionName` — {무엇을 어떻게}

## 왜 그렇게 됐나
{근본 원인. 같은 실수가 다른 데도 있는지}

## 검증
타입 ✅ / 테스트 N개 ✅ / 빌드 ✅
(회귀 테스트를 추가했으면 명시)

## 다시 확인해주세요
{사용자가 눌러볼 정확한 절차}

## 고치지 않은 것
{눈에 띄었지만 범위 밖이라 남겨둔 것}
```

## 원인을 못 찾았을 때

**추측으로 고치지 마라.** 증상만 가리는 수정은 원인을 숨겨서 나중에 더 비싸진다.

정적 코드 확인이 막히면, 순서대로:

### 1) 백엔드 공개 API부터 직접 두드려본다

신고 내용이 **백엔드가 내린 판단**(인증 거부, DB 트리거 예외, RLS 거부, 클라이언트 코드가
만들 수 없는 형식의 에러 메시지)처럼 보이면, 브라우저를 띄우거나 사용자에게 로그를 요청하기
전에 앱이 이미 공개적으로 노출하고 있는 API를 직접 두드려본다 — Supabase/Firebase 등의
anon/publishable key와 REST 엔드포인트는 배포된 클라이언트 번들 자체가 이미 공개한 것이라
추가 권한이 필요 없다.

**조건: 호출이 확실히 부작용 없을 때만.** 이미 부작용 없이 설계된 사전 확인용 RPC, 혹은
실패 시 DB가 통째로 롤백하는 호출(예: 일부러 틀린 값으로 가입 시도)만 두드린다. 실제로
데이터를 만들고·지우고·바꾸는 호출은 절대 사용자에게 먼저 묻지 않고 실행하지 않는다.

이 한 번의 curl이 클라이언트 코드를 아무리 추론해도 못 얻는 답 — 서버가 실제로 뭐라고
응답하는지 — 을 즉시 준다.

### 2) 실기기에서만 나는 화면 깨짐·레이아웃 버그는 `getComputedStyle` 배지로 확정한다

신고가 **레이아웃/렌더링**(화면 일부가 비거나 죽어 보인다, 잘린다, 겹친다) 문제이고, 정적으로
CSS를 다시 읽어도(그리드 우선순위·specificity까지 따져봐도) 세운 가설이 실기기 재현에서
계속 틀릴 때 — 두 번째 가설이 틀렸다면 세 번째 가설을 또 코드로 배포하지 말고, 의심되는
요소에 `getComputedStyle()`을 직접 걸어 `display`·실측 `width`/`height`·부모의
`grid-template-columns` 같은 값을 화면 한 구석에 찍는 **임시 디버그 배지**를 만들어
배포한다. 사용자에게 그 상태를 스크린샷 한 장으로 받으면 끝난다.

**이건 "브라우저를 띄운다"의 예외가 아니다.** 평소 배포·확인 순환(코드를 고치고 배포하면
사용자가 실행해 확인해 준다) 그대로다 — 다만 이번엔 "고친 코드"가 아니라 "측정하는 코드"를
배포하는 것뿐이다.

CSS specificity·그리드 규칙을 아무리 정확히 따져도, 그 계산 바깥에서 **전혀 다른, 스코프
안 된 규칙**(예: 셸/모드 조건 없는 `@media` 규칙이 나중에 추가된 다른 모드에도 조용히
걸리는 경우)이 이기고 있으면 정적 추론으로는 못 잡는다 — 브라우저가 실제로 계산한 값이
유일한 정답이다. 특히 원인 후보가 두 개 이상으로 갈리고 겉보기엔 화면상 완전히 똑같이
보일 때(예: "A 요소가 자기 몫을 못 받는 것"과 "B 요소가 A의 몫까지 차지해 A가 밀려난 것"은
둘 다 "A 자리가 비어 보인다"로 동일하게 보인다) 유용하다.

원인이 확정되면 **디버그 배지는 그 즉시 같은 커밋 흐름에서 제거한다** — 진단용 코드를
배포본에 남기지 않는다.

### 3) 그래도 막히면 사용자에게 요청한다

보고한다:
- 어디까지 확인했는가
- 무엇을 배제했는가
- 사용자에게 필요한 추가 정보 (콘솔 에러 메시지, 창 크기, 어느 도면, 어떤 순서)

**콘솔 에러 메시지 한 줄이 있으면 대부분 즉시 특정된다.** 없으면 요청하라.

### 4) 사용자가 그 자리에서 "브라우저로 확인해줘"라고 명시하면

**이 조사 한 건에 한해서만** "에이전트는 브라우저를 띄우지 않는다"는 기본 원칙이
풀린다 — 앞으로 계속 브라우저를 쓰라는 뜻이 아니고, 이번 진단이 막혔다는 사용자의
그 자리 판단이다. 이때도 **앱 UI를 처음부터 클릭해서 재현하기보다, 인증된 대시보드의
로그를 읽거나 백엔드 API를 직접 호출하는 쪽을 우선한다** — 로그인 상태·유효한 데이터
같은 앱 레벨 전제조건에 좌우되지 않고, 더 적은 단계로, 더 날것의 증거(원시 에러 응답)를
얻는다.

## 원인이 플랫폼 제약일 때

원인을 **찾았고 완전히 이해했는데**, 그게 코드 결함이 아니라 **플랫폼/API 자체의 한계**일
때가 있다 — 브라우저 샌드박스가 막고 있는 것, 존재하지 않는 웹 API, 네이티브 래퍼
없이는 불가능한 OS 연동 같은 것. 이 경우 "좁게 고친다"는 애초에 성립하지 않는다.

- 코드를 건드리기 전에 멈춘다
- 무엇이 기술적으로 가능하고 무엇이 불가능한지 사용자에게 있는 그대로 설명한다
- 현실적으로 가능한 대안(있다면 가장 싼 것부터)을 제시한다
- `AskUserQuestion` 또는 `_workspace/QUESTIONS.md`로 사용자의 선택을 받은 뒤 진행한다 —
  이 시점부터는 좁은 수정이 아니라 범위를 다시 정하는 대화이므로, 여기서 확정된 것은
  다음 작업의 스펙이 된다

이 분기는 "고칠 수 있는 버그 찾기"가 아니라 "이건 애초에 고칠 수 있는 종류가 아니다"라는
결론에 도달했을 때 쓴다. 여기서 즉석으로 스펙 협상까지 넓히지 말고, 정확히 위 네 단계에서
멈춘다.

## 여러 건이 한꺼번에 왔을 때

1. **먼저 분류한다** — 같은 원인인가, 별개인가
2. 같은 원인이면 하나로 묶어 한 번에 고친다
3. 별개면 **심각한 것부터** 순서대로. 데이터가 틀리는 것 > 안 되는 것 > 보기 싫은 것
4. 하나 고칠 때마다 타입·테스트를 돌린다. 몰아서 돌리면 어느 수정이 깼는지 모른다
