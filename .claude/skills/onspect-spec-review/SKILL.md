# OnSpect 스펙 검토

기획 문서를 **"이대로 코드를 쓸 수 있는가"** 기준으로 검증하고, 작업으로 분해한다.

## 왜 이 검토가 필요한가

OnSpect 기획서는 사람과의 긴 대화로 만들어졌다. 사람에게는 명확하지만
코드로 옮기려면 결정되지 않은 것이 반드시 남는다.
그 상태로 구현에 들어가면 builder 가 추측으로 메우고, 그 추측이 데이터 구조에 굳는다.

**추측이 굳기 전에 잡는 것**이 이 단계의 목적이다.

## 기준 문서 (읽는 순서)

1. `OnSpect_상세기획.md` — **1차 기준.** 데이터 모델·번호체계·Phase별 설계
2. `안전진단_결함관리앱_기획서.md` — 상위 방향. 상세기획과 충돌하면 상세기획이 우선
3. `docs/benchmark/젠트릭스_분석.md` — 경쟁 제품 실측
4. `벤치마킹 스크린샷/` — 실제 화면 14장
5. `_workspace/DECISIONS.md` — 사용자가 답한 결정 (있으면 최우선)

## 검토 절차

### 1단계 — 범위 확정

리더가 지정한 범위(예: "Phase 3 도면 캔버스")를 상세기획에서 찾는다.
범위가 지정되지 않았으면 **로드맵 표에서 🔵 표시된 Phase** 를 대상으로 한다.

### 2단계 — 고유 함정 8종 대조

이 프로젝트에서 잘못 잡으면 나중에 전부 갈아엎어야 하는 지점들이다.
검토 대상 범위가 아래 항목을 건드리면 반드시 확인한다.

| # | 함정 | 확인 질문 |
|---|---|---|
| 1 | 번호 3종 | 저장되는 번호와 계산되는 번호가 구분되어 있는가 |
| 2 | 좌표 정규화 | 마커 좌표가 0~1인가, 픽셀인가 |
| 3 | 오프라인 우선 | 쓰기가 로컬에 먼저 가는가 |
| 4 | 항목 계층 | 마스터+연결인가, 직접 종속인가 |
| 5 | 스타일 상속 | 개별 변경 시 전역에서 분리되는 규칙이 있는가 |
| 6 | 면적 단위 | mm→m 변환과 절사 규칙이 명시되어 있는가 |
| 7 | 층 sortOrder | 지하가 음수인가, 문자열 정렬인가 |
| 8 | 전회차 상태 | 3종 전이 조건이 모두 정의되어 있는가 |

### 3단계 — 3분류 판정

문서에서 발견한 것을 반드시 셋 중 하나로 분류한다. 뭉뚱그리지 않는다.

| 분류 | 정의 | 처리 |
|---|---|---|
| **모호** | 쓰여 있으나 두 가지로 읽힌다 | 두 해석과 각각의 결과를 제시 → 질문 |
| **미결정** | 문서가 아직 안 정했다고 명시 (🟡 ⬜) | 이번 범위에 필요한가? 필요하면 질문, 아니면 보류 |
| **누락** | 없는데 없으면 동작 안 한다 | 즉시 질문. **가장 위험** |

### 4단계 — 작업 분해

각 작업은 다음을 만족해야 한다.

- 산출물이 하나의 파일 또는 하나의 화면으로 말할 수 있다
- 완료 여부를 실행해서 확인할 수 있다 (`~를 만든다` 가 아니라 `~하면 ~가 보인다`)
- 다른 작업과의 의존이 명시되어 있다

**작업 크기 기준**: 한 작업이 파일 10개 이상을 건드리면 너무 크다. 쪼갠다.

### 5단계 — 질문 정리

QUESTIONS.md 에 적을 것과 그냥 정할 것을 가른다.

| 그냥 정한다 | 반드시 묻는다 |
|---|---|
| 변수·파일·폴더 이름 | 사용자가 보게 될 동작 |
| 내부 함수 분해 | 데이터 구조 |
| 코드 스타일 | 산출물의 형태 |
| 라이브러리 패치 버전 | 기획서와 어긋나는 판단 |

## 산출물

`_workspace/01_plan-reviewer_spec.md` — 형식은 `plan-reviewer` 에이전트 정의 참조.

**판정은 셋 중 하나로 명확히 낸다.**

| 판정 | 의미 |
|---|---|
| 바로 착수 가능 | 차단 질문 없음. builder 가 지금 시작해도 됨 |
| 조건부 가능 | 비차단 질문만 있음. 가정을 명시하고 시작 가능 |
| 착수 불가 | 차단 질문 있음. 답 없이 시작하면 잘못된 구조가 굳는다 |

애매하면 `조건부` 로 도망가지 말고, 무엇이 차단인지 정확히 지목한다.

## 자주 하는 실수

| 실수 | 왜 문제인가 |
|---|---|
| 기획서를 그대로 옮겨 적는다 | 검토가 아니라 복사다. 판정과 지적이 없으면 가치가 없다 |
| 모든 미결정을 질문으로 올린다 | 이번 범위에 필요 없는 것까지 물으면 사용자가 지친다 |
| "적절히 판단해서 구현" 이라고 쓴다 | builder 가 추측하게 만든다. 그 추측이 굳는다 |
| 스펙을 직접 고쳐버린다 | 기획은 사용자의 것이다. 지적하되 고치지 않는다 |
